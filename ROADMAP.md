# Roadmap

Recommended enhancements for future development, roughly ordered by priority within each section. Grouped by theme rather than a strict backlog — pick based on what matters most to whoever picks this up next.

**Status:**
- **0.2.0** shipped favorites, series progress, quick profile switching, parental controls, keyboard shortcuts for the player, DVR/catch-up, auto-reconnect, real Picture-in-Picture, a settings page, virtualized lists, debounced search, an app icon, `electron-updater` wiring, and a first pass of automated tests.
- **0.3.0** replaced the single-channel modal preview with a docked, resizable panel containing a small live video preview and a full multi-channel Gantt-style EPG grid (channels down the vertical axis, time across the horizontal axis, programmes as positioned blocks) — this also closes out the "full grid EPG guide" item that used to be listed below. The sidebar and the panel are both drag-resizable now, with widths persisted.
- **0.3.1** dropped the separate channel list on the Live TV tab entirely — the EPG grid's own channel column already lists every channel, so Live TV is now just Sidebar + a full-width grid.
- **0.4.0** added double-click-a-channel-for-fullscreen, a semi-transparent channel-swap bar overlaid on the fullscreen player (click the video to toggle it), and continuous horizontal scroll on the EPG grid's time axis (trackpad swipe / shift+wheel, in addition to the ◀ Now ▶ buttons).
- **0.4.1** fixed the channel bar being invisible in practice: `.player-body` (a flex child) had no `min-height: 0`, so flexbox's default `min-height: auto` let the video's own aspect ratio push the box taller than the actual space available — on this test stream, 112px taller than the window. That pushed everything anchored to its bottom, including the whole channel bar, off the visible window entirely, even though it existed in the DOM. Also removed the native HTML5 `controls` attribute for live channels specifically (VOD/series keep it, for scrubbing) — with it on, clicking the video both toggled play/pause *and* the bar at once (freezing the live feed), and clicking near the bottom of the video — exactly where the bar renders, and where a real user's click would land — got swallowed by the native control strip's shadow DOM before it ever reached the click handler.

- **0.4.2** fixed the EPG grid's time header appearing stuck when scrolling: ticks were generated relative to `windowStart` itself (always landing at a fixed 0/33/66/100%), so only their label text changed as you scrolled — nothing visually moved. Ticks now anchor to real clock-hour boundaries, so their on-screen position genuinely slides as the window shifts, with ticks entering/leaving at the edges. Also reworked the fullscreen channel-swap bar from plain name/icon tiles into an actual mini EPG: each cell now shows the current programme title, a Gantt-style progress bar for how far into it playback is, and a "Next:" preview — mirroring the main grid's Gantt language instead of being a flat channel switcher.
- **0.4.3** replaced the app icon — a generic play-button glyph that could've belonged to any media app — with one that actually signifies IPTV specifically: a TV set (screen + stand) receiving a broadcast signal (concentric arcs), with the play triangle kept inside the screen. Also fixed the icon never actually showing while running from source: `BrowserWindow` had no `icon` option at all, so the dev app fell back to Electron's own default logo, and on macOS the Dock icon needs `app.dock.setIcon()` specifically since `BrowserWindow`'s `icon` option only affects Windows/Linux. Packaged builds were unaffected — electron-builder already bakes `build/icon.png` into the platform installer regardless.
- **0.4.4** renamed the app to "AllisonIPTV" (window title, Dock/taskbar name, packaged bundle identity) and fixed the EPG grid's double-click-for-fullscreen only working on the channel-name button — double-clicking the programme timeline next to it did nothing, since only the inner button had the handler. Moved it to the row itself so it fires from anywhere in the row. The rename also surfaced a real near-miss: adding a root-level `productName` to package.json changes what Electron resolves as the app name *before* any of the app's own code runs, so naively "capturing the old path first" via `app.getPath('userData')` was already too late — it silently created a brand-new empty config folder under the new name instead of reusing the existing one. Fixed by reconstructing the legacy path explicitly (`appData` + `'iptv-app'`) rather than relying on the pre-rename `getPath('userData')` value.
- **0.4.5** fixed the macOS menu bar still reading "Electron" during `npm run dev` even after the rename. Turns out `app.setName()` and a custom `Menu` template's label are both silently ignored for that specific spot — macOS reads the bold system-menu-bar app name directly from the *running bundle's* `Info.plist`, not from anything Electron's JS layer can influence, so a dev-mode run (the raw `Electron.app` binary from `node_modules`) is stuck showing its own literal identity, "Electron", no matter what the app calls itself internally. Confirmed this by editing `node_modules/electron/dist/Electron.app/Contents/Info.plist`'s `CFBundleName`/`CFBundleDisplayName` directly, which *does* take effect — added `scripts/rename-dev-electron.mjs` as a `postinstall` step so the patch reapplies after every `npm install` (that directory gets fully regenerated then, wiping a one-off manual edit). macOS-only and non-fatal if it can't find the bundle. Packaged builds were never affected — their own `Info.plist` already carries "AllisonIPTV" via `build.productName`.
- **0.4.6** rebuilt the fullscreen channel-swap bar as a compact version of the main EPG grid — 5 channel rows tall (vertical axis), with its own horizontal time-scrolling Gantt timeline, instead of a single horizontal row of flat channel tiles. Clicking a channel's name or anywhere on its programme timeline switches playback immediately. This meant extracting the Gantt-grid rendering (time window state, wheel-scroll, hour ticks, the virtualized channel rows) out of `EpgGridPanel.tsx` into a new shared `EpgGrid.tsx`, since the fullscreen overlay needed the exact same mechanics, just shorter — `EpgGridPanel` now supplies the docked/full-width chrome (preview video, favorite/close buttons, resize handle) around it, and `PlayerChannelBar` supplies the semi-transparent overlay chrome around the same grid.
- **0.4.7** fixed a real screen-flicker bug on channels with a persistent (non-transient) media error — reproduced live on "101 BBC One HD London", which hit a `fragParsingError` on essentially every fragment. `Hls.ErrorTypes.MEDIA_ERROR` handling called `hls.recoverMediaError()` unconditionally, with no retry cap (unlike `NETWORK_ERROR`, which already had one) — each recovery briefly resets and re-seeks the video, and since the underlying parsing error recurred immediately every time, this looped roughly every 200ms (436 buffering-state events measured in a 20-second window), which is what actually produced the visible flicker, not real buffering. Now escalates through hls.js's own recommended recovery pattern (recover → swap audio codec + recover → give up with a clear error) and stops after 3 attempts instead of looping forever; the recovery count resets after 15 seconds of genuinely uninterrupted playback so an unrelated later blip isn't penalized. Verified: the same channel now fails cleanly with a visible error message instead of flickering forever (confirmed 0 buffering-state events over 20 seconds, down from 436), and a healthy channel plays 10+ seconds with no false give-up.
- **0.4.8** actually fixed the underlying cause instead of just failing cleanly: the `fragParsingError` on "101 BBC One HD London" (and other affected channels) turned out to be hls.js's own demuxer reporting `"Unsupported EC-3 in M2TS found"` — a hard limitation, not a corrupt segment, so no amount of retrying could ever have fixed it. Added a reactive (not blanket) fix: the fullscreen player now detects this exact pattern — either that demuxer failure or the older non-fatal `bufferAddCodecError`/`bufferAppendError` audio case — and transparently spins up a local `ffmpeg` process (bundled via `ffmpeg-static`) that remuxes just that channel's audio to AAC (video is stream-copied, not re-encoded) while showing a "Fixing audio for this channel…" message, then falls back to that output. Most channels never touch ffmpeg at all — it only spins up once a channel actually hits this specific failure. Verified end-to-end against the real account, including in an actual packaged `.app` build (the ffmpeg binary has to be unpacked from `app.asar` via `asarUnpack`, a different code path than dev mode): the same BBC channel now plays with genuine, growing decoded-audio-byte counts instead of failing, switching away kills the ffmpeg process and deletes its temp files, and a healthy channel is completely unaffected. (Follow-up: confirmed the installer size impact directly — the Windows installer grew from ~82MB to ~103MB.)
- **0.5.0** worked through most of the outstanding list in one pass: recently-watched now has a real UI (a "Recently Watched" strip above Favorites); the EPG search box also matches already-loaded programme titles, not just channel names; short-EPG fetches are capped at 4 concurrent via a queue in the store; both the main EPG grid and the fullscreen channel bar now support arrow-key/Enter navigation (`EpgGrid.tsx`, shared by both); locked categories are namespaced by section (`"live:12"` vs `"movies:12"`) with a migration that drops legacy bare IDs rather than guessing which section they meant; Escape handling is fully centralized in App.tsx (Player.tsx now only owns M/arrow-key shortcuts, eliminating the class of bug where two uncoordinated listeners raced on the same key); the channel bar now falls back to a placeholder entry if the active channel isn't in the last-browsed category; and the audio-transcode fallback (0.4.8) now also covers the small preview panel, not just the fullscreen player, via a shared `useTranscodeFallback` hook. Also fixed a real Picture-in-Picture bug found while testing: PiP already opens a genuine floating OS window (confirmed with a real desktop screenshot — it renders on top of other apps, not just inside this one), but closing the player or switching channels while PiP was open left that window floating on the desktop indefinitely, frozen on the last decoded frame; it now exits automatically, but only on a genuine channel change, not an internal same-channel reload (network reconnect, the transcode fallback), which would otherwise have kicked users out of PiP unexpectedly. Also discovered and removed a dead code path: `ChannelList.tsx` still had a full "live channel list" branch (with its own row rendering, EPG lookups, etc.) left over from before 0.3.1 removed the separate live list — App.tsx never actually renders `ChannelList` on the Live TV tab anymore, so that branch could never run.

- **0.6.2** closed the parental PIN's threat-model gap: it's now encrypted at rest via Electron's `safeStorage` (OS keychain — macOS Keychain, Windows DPAPI, Linux Secret Service where a keyring daemon is running), with new main-process IPC handlers since `safeStorage` isn't reachable from the renderer directly. Zero JS errors.

- **0.6.3** fixed the entire VOD/Series movie catalog playing with completely silent audio — confirmed via `ffprobe` sampling multiple titles that essentially every movie carries EC-3/E-AC-3 (Dolby Digital 5.1) audio, the same underlying codec 0.4.8 already handles for Live TV, but showing up completely differently here: VOD/series play through a native `<video src>` element (not hls.js), which gives no error event at all for this — the video decodes and plays perfectly, the audio track just never decodes, with nothing on `video.error` or in the console to say so. Detection is now a poll (`webkitVideoDecodedByteCount`/`webkitAudioDecodedByteCount`, requiring two consecutive silent ticks before concluding it's the codec failure rather than a startup race) since there's no error to hook into, reusing the same ffmpeg-remux-to-AAC fallback with VOD-appropriate HLS flags (`-hls_playlist_type vod`, a real end marker, instead of Live's rolling delete-and-continue window). Reaching a genuinely working fix took extensive live debugging against the real account and turned up three real bugs along the way. First: ffmpeg was auto-mapping the movie's embedded subtitle track, which made the HLS muxer defer writing the *main* playlist.m3u8 until the entire file had been processed rather than incrementally per segment — every earlier "timeout" in this investigation was actually this, not a network problem, only found by confirming live that ffmpeg fully transcoded a 76-minute movie at 19x realtime, writing hundreds of segments, while playlist.m3u8 itself never appeared until the process was killed; fixed by explicitly mapping only video+audio (`-map 0:v:0 -map 0:a:0`). Second: the proxy's `.pipe()` only ever propagates data forward, so an upstream connection was left running indefinitely once the client side abandoned it — invisible on an unlimited-connections account, but fatal on this one (confirmed via `get_server_info`: `max_connections: "1"`), since the still-open connection kept the account's single slot occupied; fixed by destroying the upstream request on any client-side close, not just success. Third: switching titles while a transcode was still spawning left the old ffmpeg process orphaned and running — the renderer only learned a session's ID once `transcode:start` resolved, which can take minutes, so `reset()` had nothing to cancel; the renderer now generates the session ID up front and registers it immediately, so a mid-flight switch actually cancels the abandoned attempt instead of leaving it to compete for the same connection slot. A fourth attempted fix — killing a transcode after a period with no ffmpeg stderr output, on the theory that silence meant it was stuck — was tried and reverted: ffmpeg's stderr is a pipe, not a tty, and its C stdio buffers a pipe's output fully rather than line-by-line, so a long silence doesn't reliably mean no progress (confirmed live, repeatedly: attempts with 60-120+ seconds of apparent silence had already opened the input and were moments from succeeding). Replaced with a single, generous flat deadline instead (240s for VOD, informed by real observed input-probe times of 25-90+ seconds on this account, against fast actual encode throughput of 19x realtime once running). Each fix was independently confirmed via live testing against the real account, but a single fully clean end-to-end pass could not be reproduced in the final verification round — the test account's connection reliability degraded visibly over the course of this debugging session (increasingly severe failure modes, ending in `net::ERR_HTTP2_PROTOCOL_ERROR` on the very first, non-transcode request), consistent with the provider throttling or rate-limiting an account reconnected dozens of times in under an hour by automated testing rather than a code issue. Worth a follow-up manual spot-check once the account has had time to rest.

- **0.6.4** found the actual root cause behind every VOD transcode timeout — 0.6.3's subtitle-mapping fix was real but wasn't it. Confirmed directly with an isolated, network-free ffmpeg test (a synthetic test pattern, no origin server involved): `-hls_playlist_type vod` is HLS-spec-correct behavior, not a bug — a VOD playlist must be published complete and unchanging per the spec, so ffmpeg withholds writing it to disk *at all* until the source hits EOF. For a two-hour movie, that's nowhere near any reasonable timeout regardless of network speed; a live test session wrote 200+ segments while `playlist.m3u8` never appeared once, then timed out right on schedule. `-hls_playlist_type event` is the type actually meant for "segments keep appending until the source ends," and writes the playlist incrementally after every segment (confirmed via ffmpeg's own log showing repeated `Opening playlist.m3u8.tmp for writing` during encode, not just at exit) — hls.js already knows to keep reloading an EVENT playlist until it sees the end marker, so this needed no player-side change at all, just the one ffmpeg flag. Also hardened the local proxy against a second, unrelated failure mode hit while chasing this down: Chromium's own network stack got stuck mid-session such that *every* request to the origin hung forever — reproduced with a plain renderer-side `fetch()` bypassing the proxy entirely hanging identically, while `curl` to the exact same URL from the same machine succeeded instantly and repeatedly, confirming the origin was healthy and something in that process's own DNS/connection state wasn't. The proxy previously had no timeout at all on the upstream request, so a hang like that was permanent, unrecoverable without restarting the app; it now gives up after 20s of no response headers, clears the session's host resolver cache, and retries once before failing. Verified end-to-end against the real account on the exact title that had been failing across every attempt: video and audio both confirmed decoding and growing in lockstep over a sustained 60+ second window, `currentTime` advancing at realtime pace, zero console errors. Worth noting for whoever picks up the next audio/transcode issue: when ffmpeg output looks stuck, check `-hls_playlist_type` (or more generally, whether the *player* mid-stream expects incremental writes) before assuming a network or connection problem — that assumption cost most of two release cycles here.

- **0.6.5** fixed a real crash a user hit directly: a "JavaScript error occurred in the main process" popup, with neither video nor audio playing. Root cause was in 0.6.4's own stuck-connection retry — `session.defaultSession.clearHostResolverCache()` returns a Promise (an IPC round-trip to the browser process), and it was being called fire-and-forget with no `.catch()`. A rejection there became an unhandled rejection in the main process, which is exactly what produces that dialog. Fixed with `.catch(() => {})`. While reproducing this, found a second, related correctness gap in the same code: the upstream timeout only called `.destroy()` on the stuck request and relied on that reliably emitting `'error'` to trigger the retry — but Electron's `net.ClientRequest`, built on Chromium's network stack rather than Node's `http` module, isn't guaranteed to fire one just because JS-side `.destroy()` was called. If it doesn't, the request stays permanently unsettled — no response, no error, and whatever's waiting on it (ffmpeg, the renderer) hangs forever, indistinguishable from the original bug the timeout exists to fix. The retry/failure logic is now a single function the timeout calls directly, guaranteeing it actually runs rather than depending on an event that might not fire. Also added global `uncaughtException`/`unhandledRejection` handlers in the main process as a safety net (previously there were none at all) — confirmed directly useful in the same test session: a genuine `net::ERR_HTTP2_PROTOCOL_ERROR` surfaced as an uncaught exception from a lower level than any per-request handler reaches, and would have crashed the app before this; instead it was logged and the retry path recovered on its own. Verified end-to-end against the real account on the exact title that had been failing and crashing: video and audio both confirmed decoding and growing over a sustained 48+ second window immediately after the retry path recovered from a live protocol error, with no crash. Lesson for next time a fire-and-forget Electron API call gets added anywhere in the main process: check whether it returns a Promise before assuming it's synchronous — `clearHostResolverCache()` looks like a simple cache-clear call and isn't one.

- **0.6.6** turned out to be a UX gap, not a functional bug, behind what looked like a fourth consecutive failure on the same title: a user report of "plays for a second then goes black, still not working" was reproduced exactly, live, repeatedly — but in every reproduction the fix actually succeeded, just not within the ~30 seconds a reasonable person would wait while staring at a small spinner. The black screen itself is intentional (the video is deliberately detached before the transcode starts, to avoid a connection conflict — see 0.6.3), but for this specific title, the audio-fix step can take anywhere from ~10 seconds to a couple of minutes depending on how the connection to the provider is behaving that moment, and the generic "Fixing audio for this channel…" wording (written with Live TV's normally-fast fallback in mind) gave no reason to expect a wait that long. Movies/series now get their own wording — "this can take a minute or two on a slow connection" — so the wait reads as expected behavior instead of a hang. Worth remembering for the next report that looks like a regression: confirm whether the underlying operation actually failed before assuming the fix regressed, especially for anything with a wait state and no progress indicator.

- **0.6.7** followed up on a report that looked like a regression but wasn't. A user hit "still not working, no video or audio" on the same title as 0.6.6, alongside two console errors: `net::ERR_NETWORK_CHANGED` (Chromium detecting a real network interface change on their machine — Wi-Fi reconnect, sleep/wake, VPN toggle; genuinely external) and `Transcode cancelled` (the fallback's own abandon-on-switch logic from 0.6.3, working as designed if the player was closed or switched mid-wait). Reproduced the exact title three times, hands-off, no interference — it succeeded every time, between ~10s and ~70s. The actual gap: 0.6.6's improved wording set the right time expectation in words, but the spinner itself still looked identical whether it was 5 seconds in or genuinely stuck, with zero real progress to report (ffmpeg is either still opening the source or still probing it during this whole window). Added a live elapsed-time counter to the message instead — the only honest signal available for a wait like this — so a user can see it's still counting rather than guessing whether it's frozen. Lesson: for a wait state with no real progress metric, don't stop at wording the uncertainty away — show the one signal that actually exists (time), or a "not stuck" report will keep looking identical to a "stuck" one.

- **0.6.8** found and fixed the real, final piece behind this whole run of VOD-transcode issues — and it took a user directly pushing back with "this title plays fine in another IPTV app" to get there, which turned out to be the key piece of evidence: another client using the same account handles this title with no issues, so the file and provider aren't the problem, meaning something in this app's own connection handling had to be. Captured a live reproduction's full console output at the user's request and found two things in the same code path. First, a real crash: the 20s upstream timeout (0.6.4) would give up on a byte-range request and answer the client, but Electron's networking sometimes *still delivered the real response* afterward — proof the connection wasn't actually dead, just slower than 20s — and that late arrival tried to write response headers a second time on an already-finished response, crashing the whole main process with `ERR_HTTP_HEADERS_SENT`. Fixed by ignoring any response that arrives after an attempt is already settled, regardless of timing. Second, given that same evidence, raised the timeout itself from 20s to 45s — 20s wasn't just occasionally too tight, it was cutting off requests that would have gone on to succeed. Notably, the reproduction that surfaced this bug *still worked* — 900+ segments over nearly 8 minutes of healthy, sustained transcoding — because ffmpeg's own internal retry happened to route around the exact race condition being fixed here. - **0.6.9** fixed the VOD/series audio-fix transcode's video visibly skipping ahead with no user input, reported live by a user actively watching. - **0.7.0** added an optional VPN feature, off by default, for routing this app's own connection to the Xtream server through OpenVPN — split-tunnel, not a full system VPN. Settings now holds a list of named profiles (each an `.ovpn` file plus optional username/password, encrypted at rest the same way as the parental PIN), with one active at a time; activating a different profile tears down the current tunnel first. The design deliberately avoids a persistent privileged daemon: connecting spawns `openvpn` via `sudo-prompt` (a one-shot elevated command, no live process handle), so control after that point goes through OpenVPN's own local management-interface socket (`--management` + `state on`) instead — auth prompts, connection-state transitions, and a clean `signal SIGTERM` shutdown all flow over that same unprivileged socket. Split-tunneling itself needed more than `--route-nopull`: a real test config (a genuine commercial VPN's `.ovpn` file) had `redirect-gateway def1` written directly in the client file, which `--route-nopull` doesn't touch since that flag only suppresses server-*pushed* routes, not the client's own. Bundling the `openvpn` binary itself (raised and explicitly declined for this release) was researched: macOS/Linux need no separate driver anymore and Windows could avoid the old TAP installer via Wintun, but there's no ffmpeg-static-equivalent source of prebuilt cross-platform OpenVPN binaries — this release continues to require it already installed. - **0.7.1** fixed a real connect failure found the moment 0.7.0 got its first genuine live test against an actual commercial VPN account: `sudo-prompt`'s elevated command failed with a content-free "Command failed" error. - **0.7.4** fixed a real Windows-only failure found on 0.7.3's first live Windows test: OpenVPN reported it couldn't find `ca.crt`/`client.crt`/`client.key` even though `--cd` correctly pointed at the directory they should have been copied into. - **0.7.5** fixed the next real Windows-only failure, found immediately after 0.7.4's cert-copy fix cleared the way: OpenVPN exited instantly with `daemon() failed or unsupported: Bad address (errno=14)`. ## VPN

- **Graceful shutdown on quit, a real toggle-by-clicking-the-dot, and a "last known configuration" concept, all at explicit request.**
  - **`before-quit` now actually waits for the tunnel to close instead of racing it.** The handler already existed (added specifically because OpenVPN, spawned via `sudo-prompt`, sits entirely outside Electron's own process tree and wouldn't otherwise be killed on quit) but called `void stopVpn()` without awaiting it — `stopVpn()` genuinely takes up to 3s (it writes `SIGTERM` to OpenVPN's management socket, then waits for the socket to actually close), so Electron's own quit sequence could tear the app down before that finished. Now `event.preventDefault()`s the first `before-quit`, awaits `stopVpn()`, and calls `app.quit()` again once it resolves — a `quittingAfterVpnStop` flag stops that second, deliberate quit from re-triggering the same guard. Live-verified via Electron's own main-process `app.evaluate()`: faking `vpnRuntime.status = 'connected'` (no real socket, so the wait branch is skipped) and quitting showed the exact expected sequence in log output (defer → `stopVpn()` resolves → re-quit) and the process actually exited (225ms, no hang); a second run confirmed the normal no-VPN-active quit path is untouched (immediate exit, no deferral logged at all).
  - **The VPN status dot (top bar and player header, same component pattern in both) is now a real toggle, not just a shortcut to Settings.** Red (`disconnected`/`error`) or amber (`connecting`) reads as "off" and a click (re)connects; green (`connected`) reads as "on" and a click disconnects — backed by a new `toggleVpnTunnel` store action shared by both dots, replacing `TopBar.tsx`'s plain `onClick={openSettings}` and `Player.tsx`'s `openVpnSettingsFromPlayer` (removed entirely, along with the fullscreen-exit dance it existed only to support — no longer needed since nothing opens the Settings modal from here anymore).   - **`lastVpnProfileId` is a new, separate setting for "reconnect to this" specifically because the existing `activeVpnProfileId` can't serve that role** — it's set on activate but explicitly cleared to `null` by `deactivateVpnProfile`, so by the time a user clicks the red dot to reconnect, the very field that used to point at "which profile" is already gone. The new field mirrors `activeVpnProfileId` on every activate but is left alone by deactivation, and is only ever cleared if that exact profile is later deleted (`removeVpnProfile`), so it can't dangle pointing at a config that no longer exists. `toggleVpnTunnel` falls back through `lastVpnProfileId` → `activeVpnProfileId` → the first saved profile, covering a user who's never connected before. - **Player/stream traffic isn't confirmed to route through the tunnel — only the API calls the connect flow itself makes.** Raised directly in 0.7.7: the local proxy's upstream request used `redirect: 'follow'`, and the split-tunnel route (0.7.0) only covers the single IP resolved for the Xtream hostname once, at connect time. If a provider's panel ever redirects actual stream delivery (not just API responses) to a different host — common with CDN-backed IPTV panels — that traffic would silently bypass the tunnel while looking, from the UI, exactly like everything else did go through it. Still not fixed, but 0.7.8 makes it instrumented rather than invisible: the proxy switched to `redirect: 'manual'` and now inspects every redirect's target host itself before following it, warning (once per off-tunnel host per connection, both to the console and as a dismissible in-app banner — `vpn:stream-route-warning`, alongside the existing disconnect warning in what's now `VpnWarnings.tsx`) whenever a hop lands somewhere other than `vpnRuntime.tunneledHost`. This still doesn't close the gap — a warned-about redirect is still followed and still bypasses the tunnel either way — it only answers the open question of whether this happens at all for a given provider.
  - **Re-examined in full via code review in 0.7.20** (no live VPN connection available to test against directly, so this is a from-the-architecture assessment, not a live confirmation) — traced exactly what a player request actually does end to end: `useAppStore.ts`'s `connect()` constructs `XtreamClient` with the *local proxy's* own base URL (`window.api.proxy.getBaseUrl()`), not the raw Xtream server — confirmed every stream URL `getStreamUrl()` builds (live, movie, series, timeshift) is proxied the exact same way API calls already were, with no separate/bypassing path. That's the good news: there's exactly one code path stream traffic can take, and it's the same one already covered by `onOffTunnelRedirect`'s instrumentation.
  - **For a provider that never redirects and whose DNS answer never changes, this traffic should genuinely be tunneled correctly** — `startVpn()` resolves the Xtream hostname once (`dns.lookup`) and adds an OS route for exactly that IP (`route add -host <ip>` / `route add <ip> mask 255.255.255.255` / `ip route del <ip>/32` — confirmed by reading `writeRouteScript` directly, all IP-based, none hostname-based), and since every player URL targets that same host through the same proxy, it rides the same route API calls do.
  - **Found a second, previously-undocumented way traffic can silently bypass the tunnel, distinct from the already-known HTTP-redirect case above — and this one has zero warning today.** The OS route above is for one *specific IP address*, resolved once via Node's own `dns.lookup()` at connect time — completely independent of Electron/Chromium's own DNS resolution and caching for the actual proxied requests. `proxyServer.ts`'s own retry-on-timeout logic calls `session.defaultSession.clearHostResolverCache()` before retrying a stuck request, deliberately forcing a *fresh* DNS lookup — if that lookup returns a different IP than the one added to the tunnel route (multiple A records, a CDN/load-balanced setup, or just ordinary DNS failover), the retried request would use the OS's normal default route for that new IP, not the tunnel, completely silently. `onOffTunnelRedirect` can't catch this: it only compares *hostnames* on an HTTP redirect, and this scenario involves the exact same hostname resolving to a different underlying IP — nothing to compare against at that layer. Chromium's own host resolver cache expiring naturally over a long viewing session (independent of anything this proxy does) is a second, milder path to the same outcome.
  - **This changes the earlier "if the warning banner never fires, close this as a non-issue" conclusion — that's no longer a safe test.** The banner only covers the redirect path; a DNS-rotation-driven bypass would produce no signal at all today. For a typical single Xtream provider server with one static, unchanging DNS record (the common case), this risk is low in practice — but it's not zero, and it's not currently observable even if it happens.
  - **What closing this for real would need**, roughly in order of effort: (1) cheapest — before each upstream request (not just after a redirect), resolve the target hostname and compare against the IP actually covered by the tunnel route, extending the existing warning to cover this case too, at least restoring visibility; (2) more complete — re-resolve and re-add the OS route (or add routes for every currently-valid IP) whenever a fresh lookup returns something new, keeping the tunnel's coverage in sync with DNS rather than freezing it at connect-time; (3) most robust but the biggest change — move away from a single-host split tunnel entirely toward routing everything through the tunnel by default with narrow exceptions for traffic that must stay local, which sidesteps the "did we route the right IP" question altogether.
  - **Option (1) implemented in 0.7.21, as a warning only — per the user's explicit request, not a fix.** `vpnRuntime.tunneledIp` (the exact IP the OS route covers, captured alongside `tunneledHost` in `startVpn`) is now compared against a fresh, independent `dns.lookup()` (`ProxyServerDeps.resolveHostIp`, deliberately Node's own resolver, not Chromium's, so it reflects a genuinely separate answer) at the same point the existing retry logic already forces a fresh DNS lookup (`clearHostResolverCache()`). A mismatch fires `onTunneledHostIpChanged`, deduped per resolved IP (`warnedTunnelIpChanges`, mirroring `warnedOffTunnelHosts`'s own pattern) and surfaced through the same `vpn:stream-route-warning` channel/banner the redirect warning already uses — no new UI needed. Covered by 3 new `proxyServer.test.ts` cases (fires on a mismatch, silent on a match, and never even checks while the VPN is reported disconnected). This still doesn't reroute anything — a warned-about mismatch still uses the normal, non-tunneled path either way — it only restores the visibility gap identified above. Options (2) and (3) remain unstarted.
- **Confirm split-tunnel routing specifically holds on Windows, not just that the tunnel connects.** 0.7.6 confirmed OpenVPN reaches a genuine CONNECTED state on Windows (green, no error) — the first real end-to-end success there — but that only proves the tunnel itself works, not that the route-up/route-pre-down `.bat` scripts (0.7.0's gateway-capture-and-restore logic, Windows-batch-syntax and never live-tested until now) actually keep ordinary browsing on the normal gateway while only the Xtream server's traffic goes through the tunnel. Worth one explicit check next time: compare `route print` before/during/after a connected session.
- **Investigate whether a failed/reconnecting VPN attempt can leave the Xtream server unreachable even after the tunnel gives up.** Reported live on Windows: after a VPN activation failed, the app's connection to the Xtream server was also lost (a 502), previously requiring a full app restart to recover — 0.7.4's Retry button fixes the *symptom* (no more restart needed), but the actual mechanism was never confirmed. One real candidate: if OpenVPN ever reaches far enough to run `--route-up` (adding a narrow host route to the Xtream server through the tunnel gateway) and then drops into `RECONNECTING` rather than exiting outright, `--persist-tun`/`--persist-key` keep that route in place while the gateway behind it is down — silently black-holing the proxy's own attempts to reach the same IP by any other path, independent of the tunnel. Worth confirming directly next time it happens: check the OS routing table for a stale host route to the Xtream server's IP while the app is in this broken state.
- **Bundling OpenVPN itself, revisited.** Explicitly declined for 0.7.0 in favor of shipping now — this release still requires OpenVPN already installed (Homebrew or Tunnelblick on macOS, the official installer on Windows/Linux). If this becomes a real onboarding friction point, the earlier research holds: macOS/Linux need no separate driver install anymore, and Windows could self-install a driver silently via Wintun instead of the old TAP installer — the actual blocker is that there's no ffmpeg-static-equivalent source of prebuilt cross-platform OpenVPN binaries, so bundling would mean standing up a real CI cross-compilation pipeline, not a quick dependency add. Also carries a GPLv2 "mere aggregation" obligation (license text + source offer for the exact binary shipped) if ever pursued — worth noting this project may already have the same unaddressed obligation from `ffmpeg-static`'s own binaries, independent of OpenVPN.

## Playback quality

- **A "channel is currently broken" surface.** Still relevant for whatever *doesn't* get fixed by the transcode fallback (a genuinely dead stream, an unsupported video codec, etc.) — there's still no way to know a channel is bad without trying it. Nothing to build proactively here yet (no data on how common this is across a real catalog), but worth watching if it turns out to affect more than a handful of channels.
- **The proxy's stuck-connection retry (0.6.4) is still a mitigation, not a confirmed single root cause — because there turned out to be more than one.** 0.6.8 directly proved at least one contributing case: a request some code path was treating as "hung" was actually just slower than the timeout allowed, with a real response arriving late. That doesn't rule out the *other* mechanism 0.6.4 was chasing (every request to a host hanging forever with zero response at all, reproduced independently of this proxy) — the two may well be separate failure modes that happen to look similar from a fixed timeout's perspective. If a hang recurs in a way 45s + one retry doesn't catch, the next step is still capturing a `chrome://net-export` log from a live reproduction rather than tuning the timeout again — that's the only way to tell which mechanism (or a third one) is actually in play this time.
- **Lighter-weight ffmpeg bundling — a system-ffmpeg-if-present check shipped in 0.7.13, but it does *not* reduce the installer size, and was never going to.** Confirmed in 0.4.8: bundling `ffmpeg-static` grew the Windows installer from ~82MB to ~103MB. `ffmpegResolver.ts` now prefers a working system-installed ffmpeg over the bundled copy at runtime (checked once per launch, cached — common install locations first for the same reason `findOpenvpnBinary` checks them directly, since a macOS app launched from Finder/Dock doesn't inherit a shell's PATH, then a `which`/`where` lookup, then a cheap `-version` spawn to confirm it's a real, working ffmpeg before trusting it over the known-good bundled one). But the bundled binary still ships in every installer unconditionally regardless of whether it ever actually runs — packaging decides what's *in* the installer, not which binary gets executed at runtime, and removing it would mean the audio-fix fallback simply stops working for anyone without a system ffmpeg (likely the more common case, especially on Windows), which is a real regression traded for a size saving only some users would even see. So this closes the "redundant copy of ffmpeg running on a system that already has one" concern, but the installer-size number from 0.4.8 is unchanged and the roadmap item's own premise (that this would address it) doesn't actually hold — an honest correction now that it's been built, not before.
- **Subtitles are dropped entirely once the VOD/series audio-fix transcode kicks in (0.6.3).** The fallback explicitly maps only video+audio (`-map 0:v:0 -map 0:a:0`). Investigated properly in 0.7.10 with isolated, network-free ffmpeg tests (synthetic video+AC-3 audio+SRT subtitle input, run directly against the exact bundled `ffmpeg-static` 6.0 binary this app ships) rather than attempted blind — found real progress, but also a real blocker that's still unresolved:
  - Mapping the subtitle track (`-map 0:s:0 -c:s webvtt`) alongside video+audio in a flat `-f hls` output (no `-var_stream_map`) does *not* reproduce 0.6.3's deferred-playlist bug on this ffmpeg version — `playlist.m3u8` still writes incrementally, confirmed the same way 0.6.4 confirmed the original bug (watching segments accumulate in real time via a `-re`-throttled synthetic input). Whatever caused the original bug, it either doesn't reproduce with an explicit `-c:s webvtt` codec, or was specific to a subtitle format/ffmpeg version this test didn't reproduce.
  - That flat layout is a dead end anyway: its WebVTT rendition (`playlist_vtt.m3u8`) is never referenced anywhere inside the flat `playlist.m3u8` a player is actually given, so it's structurally undiscoverable — a real HLS master playlist (`-var_stream_map "v:0,a:0,s:0,sgroup:subs"` + `-master_pl_name`) is genuinely required for a player to ever find the subtitle track at all. Confirmed that layout *also* writes everything incrementally when a subtitle stream exists.
  - The actual blocker: `-var_stream_map` referencing `s:0` hard-fails the whole ffmpeg process ("Unable to map stream at s:0") the instant the source has no subtitle track — even with ffmpeg's own optional-map syntax (`-map 0:s:0?`) correctly producing zero subtitle output streams first. Confirmed with matched pairs of tests (same command, one input with a real subtitle track, one without). A from-one-input two-separate-outputs workaround (video+audio always, an independent optional subtitle-only `-f hls` output) was also tried and found *unreliable in the opposite direction* — it failed ("No streams to mux were specified") specifically when a subtitle track *was* present and mapped, the reverse of what's needed, and not chased further without understanding why.
  - So safely choosing the right ffmpeg command shape requires knowing up front whether the source has a mappable subtitle track — and there's no cheap way to know that. This app's own Xtream API calls carry no subtitle metadata (there's no `get_vod_info` call today, and Xtream panels don't expose per-stream subtitle presence at the catalog level regardless), so the only way to find out is to actually open the file — the same expensive step (25-90s observed on this account, per 0.6.3) `startTranscode` already treats as its dominant cost. A "try with subtitles, retry without on the specific failure" approach would be *correct* (the failure happens fast, right after the initial probe, before any output exists) but would double that wait for every title that doesn't have embedded subtitles — likely the common case — which is a real regression traded for a minority-case feature, not a free win.
  - Not attempted further that round. Next step would be either finding a genuinely cheap way to know subtitle presence before committing to a muxer layout, or live-testing the double-open-cost trade-off against a real account to see whether it's actually acceptable in practice rather than assuming it isn't.
  - **Solved in 0.7.18, with a genuinely cheap way to know subtitle presence: ffmpeg already tells us, for free, at the exact moment it's worth knowing.** The "up front" framing above was the wrong question — `startTranscode` already pays the 25-90s cost of opening the source regardless (that's inherent to how this fallback works, not something to avoid), and ffmpeg prints the source's full stream list (including any `Stream #N: Subtitle: ...` line) to stderr the moment it finishes that open, well before it writes a single output segment. `transcodeService.ts` now watches for that line (`SUBTITLE_STREAM_PATTERN`) instead of trying to find out separately, so there's no second probe, no doubled connection, and no behavior change at all for the (likely more common) no-subtitle case. The VOD/series argv unconditionally adds `-map 0:s:0? -c:s webvtt` (optional-map syntax, so it's a no-op when there's no subtitle track); if `subtitleDetected` fires, `startTranscode` waits (capped at `subtitleGraceMs`, 5s in production — never lets a broken/slow subtitle rendition hold up or fail an otherwise-ready video) for ffmpeg's own `playlist_vtt.m3u8` sidecar to appear, then writes a small master playlist itself (`master.m3u8`, `EXT-X-MEDIA:TYPE=SUBTITLES` + `EXT-X-STREAM-INF`) to make that sidecar discoverable — deliberately not using `-var_stream_map` for this, since that's the exact thing confirmed in 0.7.10 to hard-fail outright when a source has no subtitle stream. `index.ts`'s `transcode:start` handler now returns whichever filename `startTranscode` actually produced (`basename(playlistPath)`) instead of a hardcoded `playlist.m3u8`, which had been silently ignoring `startTranscode`'s own return value.
  - **A real near-miss caught by testing, not assumed away:** an initial version of this fix's own integration test (a synthetic subtitle track with one cue spanning nearly the whole clip) reproduced the *exact* deferred-write bug this feature exists to avoid — `playlist.m3u8` didn't appear until the entire clip had been read, confirmed with the same real-time-paced (`-re`) isolated ffmpeg technique 0.6.4 used originally. Root-caused directly, not guessed at: a realistic subtitle track (several short cues spread across the clip, the way any real movie's subtitle file actually looks — not one giant cue) writes `playlist.m3u8` incrementally exactly like the no-subtitle case, confirmed with a second isolated `-re` run. The earlier 0.7.10 note above claiming this combination "does not reproduce the deferred-playlist bug" was evidently only checked against a fixture shaped like a real subtitle track too, by luck rather than an explicit test of the single-long-cue case — this round's own test fixture (`transcodeService.test.ts`) now uses six short, evenly-spaced cues specifically so it can't silently regress back to the single-cue failure mode without the test catching it.
  - Verified: 3 new unit tests against the fake-ffmpeg fixture (master playlist returned once both files exist; falls back to the plain playlist if the subtitle rendition never actually appears within `subtitleGraceMs`; a Live TV session ignores a detected subtitle stream entirely rather than waiting on a rendition its own argv never requested), plus a new real-ffmpeg integration test building an actual video+AC-3+multi-cue-SRT `.mkv` fixture and running it through the genuine bundled `ffmpeg-static` binary end to end — confirms the real master playlist references the real generated `playlist_vtt.m3u8`, and that file is genuine WebVTT. All of this is synthetic/local-only, same as every other ffmpeg integration test in this suite — no real account was touched testing this.
  - **Live-tested against the real account immediately after writing the above — and it caught a real, serious bug the synthetic tests never could.** Batman Begins (already known from the earlier investigation to need this fallback) turned out to genuinely have an embedded subtitle track: `subtitleDetected` fired, `master.m3u8` got built and requested exactly as designed. But the very first real attempt broke playback entirely — hls.js abandoned the session with `fragLoadError` after 4 retries, `seg_00000.ts` and the subtitle cue file `playlist0.vtt` both stuck in a repeated-request loop. Cause: `serveTranscodeFile`'s `TRANSCODE_MIME_TYPES` table only had `.m3u8`/`.ts` entries — every one of ffmpeg's per-segment WebVTT cue files (`playlist0.vtt`, `playlist1.vtt`, ...) 404'd through the local proxy, and hls.js treated that as fatal for the whole session rather than just disabling captions. Added `.vtt: 'text/vtt'` and a unit test serving one directly. Re-tested live immediately after: no more `fragLoadError`, segments and cue files (25 of each, `seg_00000.ts` through `seg_00024.ts`) loaded cleanly and continuously over 45+ seconds of real encode progress with zero errors.
  - **What's genuinely confirmed vs. not, after that live round:** subtitle detection, master-playlist construction, and — critically — the fixed MIME bug are all confirmed against the real account and a real title, not just synthetic fixtures. What's *not* confirmed: the CDP-driven test script watched `video.currentTime`/`readyState` for 45 seconds after the master playlist loaded and never saw either advance from 0, despite the healthy, continuous segment fetching. Left deliberately unresolved rather than guessed at — most likely explanation is that automating this through CDP doesn't reliably reproduce a real user session's autoplay/interaction state (this exact fallback's ordinary, non-subtitle path was already confirmed genuinely playing for the user directly, immediately before this round of work started), but a real stall specific to loading a *master* playlist rather than a flat one hasn't been ruled out either. Didn't spend a fourth live connection attempt chasing it given the account's one-connection limit — next step is simply watching for it (does the picture actually appear, do captions toggle on) the next time this fallback fires naturally during real use.
  - **Resolved the open question above the next day**: the user confirmed captions genuinely display during real use (so the `currentTime`-not-advancing observation above really was just a CDP-automation artifact, not a real playback stall). But that surfaced the next real gap — no on/off toggle or track picker exists for these subtitles; see the new item under Player controls.
- **A single-connection account puts Live TV's and VOD's audio-fix fallbacks in the same failure class — now confirmed live, and worse than assumed.** 0.6.3 traced VOD's transcode timeouts back partly to a real account cap (`get_server_info`: `max_connections: "1"`) combined with a proxy bug that left an abandoned connection open indefinitely — now fixed, but the underlying constraint (one slot, shared by whatever's currently playing and whatever ffmpeg needs to open) isn't going away for accounts like this one. 0.7.9 surfaced this rather than leaving it silent (`singleConnectionAccount`, the VOD "Fixing…" secondary line, the appended failure explanation) but left it unverified against a real repro.
  - **Live-verified in 0.7.15** on a real single-connection account against a real title (a movie whose audio-fix fallback kept failing for the user): the existing silent-audio detection correctly fired (video decoding, audio not — the classic EC-3/AC-3 case), correctly triggered the ffmpeg fallback, and the `singleConnectionAccount` hint correctly appeared at 60s — all working exactly as designed. But the fallback itself then ran for the *entire* 240s VOD deadline and failed with "Timed out waiting for ffmpeg to produce transcoded output," never even opening the source.
  - Tried bumping `CONNECTION_RELEASE_DELAY_MS` from 2s to 8s (the delay between detaching the original `<video>` and letting ffmpeg try to open its own connection) on the theory that 2s wasn't enough time for the origin to notice the old connection was gone. Reproduced the identical failure again, at the identical full-240s timeout, with no difference — ruling out "the origin just needed a few more seconds" as the explanation. Kept the 8s value anyway (matches the documented concern this constant already existed for, and costs nothing but a slightly longer wait before the fallback starts trying), but it demonstrably didn't fix this repro.
  - Genuinely unresolved: since ffmpeg never exits (a "timed out" result, not "exited with an error"), it's stuck trying to open the connection for the *entire* 4-minute window, not just delayed briefly at the start — which points toward something more persistent than a quick release race, e.g. a provider-side cooldown/session-lock on the account lasting well beyond a few seconds, or this specific title being broken/unreachable on the provider's end independent of the connection cap at all. Also can't rule out that the live-testing itself (three connection attempts to the same single-connection account within about 15 minutes, to reproduce and then test a fix) put the account into exactly this kind of locked-out state — deliberately stopped testing further to avoid compounding that rather than guessing at more delay values against a possibly self-confounded repro.
  - **Found and fixed the actual mechanism in 0.7.16**, prompted by a second live report from the same user: after the failed Batman Begins fallback, the *entire app* — menus, categories, other streams, everything — stopped working too, not just that one title. That's a much bigger clue than "one title is broken," and led to a real, confirmed bug, not just another theory: `proxyServer.ts`'s cleanup logic called `upstreamReq.destroy()` on timeout/client-disconnect to release the connection — but for a request that had followed even one redirect, Electron's `net.ClientRequest.destroyed` reports `true` *before anything has cancelled it*, and calling `.destroy()` on it is a silent no-op — the underlying connection to the redirect target is never actually closed. Confirmed directly with an isolated, no-live-account-involved reproduction (a real Electron `net.request` against local mock servers: one that redirects, one that then hangs forever) — `.destroy()` left the hanging server's connection open forever; `.abort()` closed it correctly, in both the redirected and non-redirected cases, and proved safe to call more than once or after a request already completed. Since Electron's `net` module shares one connection pool per host across the *entire app*, a single leaked connection from one failed VOD fallback attempt could starve every other request to the same Xtream server — exactly the second symptom reported. Switched both cleanup call sites to `abort()`; a new `proxyServer.test.ts` case covers the orchestration logic (redirect → hang → timeout → retry → give up) end-to-end, though it can't reproduce the Electron-specific `destroy()`-after-redirect quirk itself (that lives entirely inside Electron's own net module, outside what a plain Node/vitest test can exercise) — verified only via the one-off isolated script, not as a permanent regression test.
  - This is a strong, confirmed fix for the *second* symptom (everything breaking afterward) — a leaked connection permanently occupying a single-connection account's one slot until the whole app restarts matches that exactly. Whether it also fixes Batman Begins *itself* playing is less certain: if the file simply redirects to a CDN host that's slow/unreliable for reasons outside this app's control, retries will still eventually give up, just without leaving the rest of the app broken behind them. Needs the user to fully quit and restart the app first (a leaked connection from *before* this fix wouldn't be helped by code that only runs on the *next* attempt — the OS only reliably reclaims it on process exit) and try again.
  - **Found a second, unrelated, and much simpler bug in 0.7.17 — this one a genuine app-wide crash, not a connection leak.** The user's dev session went to a black screen with no visible error mid-session; DevTools console (the user opened it directly and pasted the output, since the already-running process had no remote-debugging port to attach to) showed `Uncaught Error: Illegal hls.js config: "liveMaxLatencyDurationCount" must be greater than "liveSyncDurationCount"` thrown from `new Hls(...)` in `Player.tsx`. The non-live branch (movies/series, including this exact ffmpeg-fallback `.m3u8` output) set both values to the identical `1_000_000` — meant as "effectively infinite, disable live-edge seeking" (see the 0.6.x-era comment above it), but hls.js's constructor validates `liveMaxLatencyDurationCount` strictly greater than `liveSyncDurationCount` and throws synchronously otherwise. With no error boundary anywhere above `<Player>`, React unmounted the *entire* app on that uncaught error — a blank screen with no buttons and no visible error was the correct, if alarming, description of exactly what happened. Fixed by giving the two "infinite" values distinct numbers (`1_000_000` / `2_000_000`) so both still functionally disable live-edge behavior for VOD/series while satisfying hls.js's check. Also added a `PlayerErrorBoundary` around `<Player>` so a future bug in this class fails to "playback closed, with a message" instead of "the whole app is gone" — defense in depth, not a substitute for the actual fix. This is a plausible *third* contributor to the original Batman Begins reports (on top of the two already documented above): if the ffmpeg-fallback path was ever reached, this line would have thrown every single time, unconditionally, regardless of the account's connection limit or anything CDN-side — worth keeping in mind if Batman Begins itself still doesn't play cleanly after 0.7.16 + 0.7.17 together.

  - **New `UpdatePrompt.tsx`**, styled with the same `.modal-overlay`/`.modal-card`/`.pin-actions`/`.secondary-button` classes `PinPrompt`/`AboutModal` already use, mounted at `App.tsx`'s root next to those. Three states off one `updateInfo`/`updateDownloadPercent`/`updateDownloaded`/`updateError` set of store fields: **available** ("Version X.Y.Z is available" + Update Now/Later, with any download error shown inline rather than a separate dialog), **downloading** (a plain percent-width progress bar, no cancel — matching this app's existing "Fixing playback…" spinner's own no-cancel precedent), and **downloaded** ("Restart to finish installing" + Restart Now/Later). `AboutModal.tsx` also gained a "Check for Updates" button for a manual re-check, using its own local `checking` state so the button's temporary "Checking…" label can't be confused with `updateInfo` actually finding something (that always surfaces via `UpdatePrompt` itself, wherever the user is, not just inside the About modal).
  - **A real bug caught by live UI testing before it shipped, not just reasoned about.** The original render guard read `if (dismissed && !downloaded) return null` — intended to make a downloaded update resurface even past an earlier "Later" on the plain available-prompt, but its actual effect was that *nothing* could ever dismiss the downloaded-prompt either, since the guard unconditionally kept showing it whenever `downloaded` was true, including after clicking its own "Later" button. Caught immediately by scripting the exact click and checking the DOM afterward (`goneAfterLater` was `false` right after clicking Later on the downloaded state — plainly wrong). Fixed by moving the "resurface past a dismissal" behavior to where it actually belongs — the `update:downloaded` handler in the store resets `updateDismissed: false` itself, matching what `update:available`'s handler already did — which let the component's own guard simplify to a single, uniform `if (!updateInfo || dismissed) return null` that behaves correctly for both prompts.
  - **Testing strategy, and a hard lesson from the VPN toggle work carried forward.** `useAppStore.test.ts` gained 5 new Electron-free unit tests for the action layer (`checkForUpdates` clearing a stale error, `downloadUpdate` setting progress to 0 immediately and recording a real failure, `installUpdate` and `dismissUpdatePrompt`), same mocking pattern as the VPN toggle tests. The actual `UpdatePrompt` UI states (available/downloading/downloaded/error, and the dismiss-behavior bug above) were verified live in the real packaged app instead — this project has no component-test tooling — but deliberately *only* by writing directly into the store's fake state (`updateInfo`, `updateDownloadPercent`, etc.) and never by calling `checkForUpdates`/`downloadUpdate`/`installUpdate` themselves, since those hit the real, contextBridge-frozen `window.api.updater` exactly the way an earlier attempt to stub `window.api.vpn` silently failed and triggered a real OpenVPN connection instead (see VPN's own account of that incident) — `installUpdate` in particular calls `quitAndInstall()`, which was never going to be a safe thing to trigger against a dev build with nothing genuine downloaded.
- **Code signing & notarization.** Unsigned installers trigger Gatekeeper warnings on macOS and SmartScreen warnings on Windows — and macOS's Squirrel-based auto-updater specifically **won't apply updates at all** to an unsigned/unnotarized app, so this is a hard blocker for auto-update actually working on Mac, not just a polish item. Needs a paid Apple Developer certificate and (for Windows) a code-signing certificate; plug into `.github/workflows/release.yml` once available.
- **Windows on ARM installer — blocked, not just niche.** `ffmpeg-static`'s platform table (`node_modules/ffmpeg-static/index.js`) only lists `x64`/`ia32` for `win32`; there's no `arm64` Windows binary to bundle at all. Building one anyway would either fail the install step outright or silently package the x64 binary into an arm64 installer, which would only work via Windows' x64-emulation layer — not a real native build. Revisit only if `ffmpeg-static` adds arm64 Windows support upstream, or if the lighter-weight-ffmpeg-bundling item above ships first and changes what's actually being packaged.

## Quality

- **Expand test coverage.** vitest unit tests exist for `lib/xtream.ts`, `lib/epg.ts`, `lib/epgTime.ts` (the EPG grid's `pct()` math), `lib/storage.ts` (settings load/merge, locked-category migration, PIN encryption fallback), `lib/useTranscodeFallback.ts` (`isUnsupportedAudioCodecError`), and `useAppStore.ts` (locked-category namespacing, `submitPinAttempt`'s PIN comparison, the short-EPG concurrency queue's actual cap, `tvArchive` threading through `play()`), plus a CI job that runs typecheck/lint/test/build on every push. 0.7.11 closed the proxy gap named here previously: `startLocalProxy()`'s request-handling logic (retry/timeout, CORS/header rewriting, off-tunnel-redirect detection) moved out of index.ts's `handleProxyRequest` closure into a new `src/main/proxyServer.ts` — an extract-and-parameterize refactor, not a rewrite (every comment and the exact retry/timeout/redirect behavior moved verbatim), with all of its Electron dependencies (`net.request`, `session.defaultSession.clearHostResolverCache`, VPN state, transcode-file serving) injected via a `ProxyServerDeps` object instead of referenced directly. That makes the module fully Electron-free and testable against a real local HTTP server — `proxyServer.test.ts` spins one up per test plus a genuine Node `http.request`-backed stand-in for Electron's `net.request` (a real `EventEmitter`, since `req.pipe(upstreamReq)` needs generic stream-event support, not just the three custom events this code actually listens for), and covers CORS/OPTIONS handling, malformed-target-URL handling, Range forwarding, content-encoding/length/CSP stripping, the off-tunnel-redirect callback (fires only when genuinely cross-host *and* the VPN is connected, confirmed both negative cases), and the timeout+retry path actually recovering on the second attempt (with `upstreamTimeoutMs` made injectable so the test doesn't wait out a real 45s timeout) — 64 tests total as of 0.7.11. One real Electron-`.d.ts` gap surfaced along the way and got documented rather than worked around silently: `net.request()`'s bundled type declares only the older `.abort()`, omitting `.destroy()`/`.destroyed` even though both have genuinely existed and worked at runtime across many prior releases of this exact proxy — bridged with one explicit, commented cast at the single call site that constructs a real one, rather than loosening the new module's own interface to paper over it. 0.7.13 extracted and tested a second slice the same way: `ffmpegResolver.ts` (the system-ffmpeg-preferred-over-bundled logic, see Playback quality below) took its file-existence/process-spawning dependencies as injected parameters from the start rather than needing a later extraction pass, with `ffmpegResolver.test.ts` covering the common-location/PATH-lookup fallback chain, the `-version` usability check, and the resolve-once caching — including one real integration check against the actual bundled `ffmpeg-static` binary, not just hand-shaped fake stdout. 0.7.14 closed the last of the three main-process extractions this pass was working through: `startTranscode`/`stopTranscode`/`serveTranscodeFile` moved from index.ts into `src/main/transcodeService.ts` the same way (deadlines/poll-interval injectable, session state owned per-instance rather than module-level, so tests get a fresh isolated service each time). `transcodeService.test.ts` uses a tiny fake-ffmpeg shell script (behavior picked via an env var, since the real, fixed argv shape can't be varied per test) for the control-flow cases — missing binary, cancellation racing a not-yet-started session, a clean exit, a fatal exit, a genuine timeout, cleanup — plus one real integration test against the actual bundled ffmpeg-static binary and a synthetic AC-3 input, mirroring 0.7.10's own real-ffmpeg verification approach. That integration test surfaced a genuine, if practically unreachable, race in the process it was testing: `startTranscode`'s `proc.on('exit', ...)` handler deletes the whole temp directory on *every* exit, including success, and an unrealistically fast local remux (a small `-c:v copy` job with no real network latency) can finish before the poll loop's own `existsSync` check ever runs, losing the race to that cleanup. Real movies/episodes never trigger this — reading and remuxing an actual file takes far longer than one poll interval regardless of copy-mode speed — so the fixture was made more realistic (a throttled synthetic origin simulating real network delivery) instead of changing the production code it was accidentally stress-testing. Suite goes from 100 to 113 tests. Still untested: most of the rest of the store's actions (`connect`/`init`'s own control flow, VPN profile CRUD) — the only main-process code with real historical bug density left fully coupled to Electron is gone now.
- **A floating-promise lint rule would have caught 0.6.5's crash before it shipped — added in 0.7.9.** `eslint.config.mjs` now runs `@typescript-eslint/no-floating-promises` (and `no-misused-promises`, scoped off for JSX attributes/props specifically to avoid flagging this codebase's own idiomatic `onClick={async () => ...}` pattern) across both the main/preload and renderer source trees, wired into CI as a new `npm run lint` step right after `typecheck`. Turning it on surfaced 17 genuine pre-existing floating promises — mostly fire-and-forget calls to this store's own `save*`/`load*` helpers and to Electron APIs (`shell.openExternal`, `BrowserWindow.loadURL`/`loadFile`, `app.whenReady().then(...)`) — each fixed on a case-by-case basis: an explicit `void` for calls into something that already self-catches (e.g. `selectCategory`, `loadShortEpg`), a `.catch()` with a specific log message everywhere else, and one real gap closed along the way — `init()` itself had no top-level try/catch, so a storage-read failure during startup would have silently stuck the app on its initial screen with nothing but a console error; it now falls back to the same `status: 'error'` banner `connect()` already uses.
- **React's `autoFocus` doesn't work for dynamically-mounted elements.** A real gotcha hit while building 0.5.0's channel-bar keyboard nav: the JSX `autoFocus` prop relies on the browser's native autofocus-on-parse behavior, which only fires for elements present in the *initial* HTML parse — not for ones a React component inserts later via the DOM API, which describes almost every conditionally-mounted overlay in this app. `EpgGrid.tsx` now calls `.focus()` explicitly in a mount effect instead, and that's now the established pattern for anything else in this codebase that wants to autofocus on mount.
