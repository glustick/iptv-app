# Roadmap

Recommended enhancements for future development, roughly ordered by priority within each section. Grouped by theme rather than a strict backlog — pick based on what matters most to whoever picks this up next.

**Status:**
- **0.2.0** shipped favorites, series progress, quick profile switching, parental controls, keyboard shortcuts for the player, DVR/catch-up, auto-reconnect, real Picture-in-Picture, a settings page, virtualized lists, debounced search, an app icon, `electron-updater` wiring, and a first pass of automated tests.
- **0.3.0** replaced the single-channel modal preview with a docked, resizable panel containing a small live video preview and a full multi-channel Gantt-style EPG grid (channels down the vertical axis, time across the horizontal axis, programmes as positioned blocks) — this also closes out the "full grid EPG guide" item that used to be listed below. The sidebar and the panel are both drag-resizable now, with widths persisted.
- **0.3.1** dropped the separate channel list on the Live TV tab entirely — the EPG grid's own channel column already lists every channel, so Live TV is now just Sidebar + a full-width grid.
- **0.4.0** added double-click-a-channel-for-fullscreen, a semi-transparent channel-swap bar overlaid on the fullscreen player (click the video to toggle it), and continuous horizontal scroll on the EPG grid's time axis (trackpad swipe / shift+wheel, in addition to the ◀ Now ▶ buttons).
- **0.4.1** fixed the channel bar being invisible in practice: `.player-body` (a flex child) had no `min-height: 0`, so flexbox's default `min-height: auto` let the video's own aspect ratio push the box taller than the actual space available — on this test stream, 112px taller than the window. That pushed everything anchored to its bottom, including the whole channel bar, off the visible window entirely, even though it existed in the DOM. Also removed the native HTML5 `controls` attribute for live channels specifically (VOD/series keep it, for scrubbing) — with it on, clicking the video both toggled play/pause *and* the bar at once (freezing the live feed), and clicking near the bottom of the video — exactly where the bar renders, and where a real user's click would land — got swallowed by the native control strip's shadow DOM before it ever reached the click handler.

- **0.4.2** fixed the EPG grid's time header appearing stuck when scrolling: ticks were generated relative to `windowStart` itself (always landing at a fixed 0/33/66/100%), so only their label text changed as you scrolled — nothing visually moved. Ticks now anchor to real clock-hour boundaries, so their on-screen position genuinely slides as the window shifts, with ticks entering/leaving at the edges. Also reworked the fullscreen channel-swap bar from plain name/icon tiles into an actual mini EPG: each cell now shows the current programme title, a Gantt-style progress bar for how far into it playback is, and a "Next:" preview — mirroring the main grid's Gantt language instead of being a flat channel switcher.
- **0.4.3** replaced the app icon — a generic play-button glyph that could've belonged to any media app — with one that actually signifies IPTV specifically: a TV set (screen + stand) receiving a broadcast signal (concentric arcs), with the play triangle kept inside the screen. Also fixed the icon never actually showing while running from source: `BrowserWindow` had no `icon` option at all, so the dev app fell back to Electron's own default logo, and on macOS the Dock icon needs `app.dock.setIcon()` specifically since `BrowserWindow`'s `icon` option only affects Windows/Linux. Packaged builds were unaffected — electron-builder already bakes `build/icon.png` into the platform installer regardless.
- **0.4.4** renamed the app to "AllisonIPTV" (window title, Dock/taskbar name, packaged bundle identity) and fixed the EPG grid's double-click-for-fullscreen only working on the channel-name button — double-clicking the programme timeline next to it did nothing, since only the inner button had the handler. Moved it to the row itself so it fires from anywhere in the row. The rename also surfaced a real near-miss: adding a root-level `productName` to package.json changes what Electron resolves as the app name *before* any of the app's own code runs, so naively "capturing the old path first" via `app.getPath('userData')` was already too late — it silently created a brand-new empty config folder under the new name instead of reusing the existing one. Fixed by reconstructing the legacy path explicitly (`appData` + `'iptv-app'`) rather than relying on the pre-rename `getPath('userData')` value.
- **0.4.5** fixed the macOS menu bar still reading "Electron" during `npm run dev` even after the rename. Turns out `app.setName()` and a custom `Menu` template's label are both silently ignored for that specific spot — macOS reads the bold system-menu-bar app name directly from the *running bundle's* `Info.plist`, not from anything Electron's JS layer can influence, so a dev-mode run (the raw `Electron.app` binary from `node_modules`) is stuck showing its own literal identity, "Electron", no matter what the app calls itself internally. Confirmed this by editing `node_modules/electron/dist/Electron.app/Contents/Info.plist`'s `CFBundleName`/`CFBundleDisplayName` directly, which *does* take effect — added `scripts/rename-dev-electron.mjs` as a `postinstall` step so the patch reapplies after every `npm install` (that directory gets fully regenerated then, wiping a one-off manual edit). macOS-only and non-fatal if it can't find the bundle. Packaged builds were never affected — their own `Info.plist` already carries "AllisonIPTV" via `build.productName`.
- **0.4.6** rebuilt the fullscreen channel-swap bar as a compact version of the main EPG grid — 5 channel rows tall (vertical axis), with its own horizontal time-scrolling Gantt timeline, instead of a single horizontal row of flat channel tiles. Clicking a channel's name or anywhere on its programme timeline switches playback immediately. This meant extracting the Gantt-grid rendering (time window state, wheel-scroll, hour ticks, the virtualized channel rows) out of `EpgGridPanel.tsx` into a new shared `EpgGrid.tsx`, since the fullscreen overlay needed the exact same mechanics, just shorter — `EpgGridPanel` now supplies the docked/full-width chrome (preview video, favorite/close buttons, resize handle) around it, and `PlayerChannelBar` supplies the semi-transparent overlay chrome around the same grid.
- **0.4.7** fixed a real screen-flicker bug on channels with a persistent (non-transient) media error — reproduced live on "101 BBC One HD London", which hit a `fragParsingError` on essentially every fragment. `Hls.ErrorTypes.MEDIA_ERROR` handling called `hls.recoverMediaError()` unconditionally, with no retry cap (unlike `NETWORK_ERROR`, which already had one) — each recovery briefly resets and re-seeks the video, and since the underlying parsing error recurred immediately every time, this looped roughly every 200ms (436 buffering-state events measured in a 20-second window), which is what actually produced the visible flicker, not real buffering. Now escalates through hls.js's own recommended recovery pattern (recover → swap audio codec + recover → give up with a clear error) and stops after 3 attempts instead of looping forever; the recovery count resets after 15 seconds of genuinely uninterrupted playback so an unrelated later blip isn't penalized. Verified: the same channel now fails cleanly with a visible error message instead of flickering forever (confirmed 0 buffering-state events over 20 seconds, down from 436), and a healthy channel plays 10+ seconds with no false give-up.
- **0.4.8** actually fixed the underlying cause instead of just failing cleanly: the `fragParsingError` on "101 BBC One HD London" (and other affected channels) turned out to be hls.js's own demuxer reporting `"Unsupported EC-3 in M2TS found"` — a hard limitation, not a corrupt segment, so no amount of retrying could ever have fixed it. Added a reactive (not blanket) fix: the fullscreen player now detects this exact pattern — either that demuxer failure or the older non-fatal `bufferAddCodecError`/`bufferAppendError` audio case — and transparently spins up a local `ffmpeg` process (bundled via `ffmpeg-static`) that remuxes just that channel's audio to AAC (video is stream-copied, not re-encoded) while showing a "Fixing audio for this channel…" message, then falls back to that output. Most channels never touch ffmpeg at all — it only spins up once a channel actually hits this specific failure. Verified end-to-end against the real account, including in an actual packaged `.app` build (the ffmpeg binary has to be unpacked from `app.asar` via `asarUnpack`, a different code path than dev mode): the same BBC channel now plays with genuine, growing decoded-audio-byte counts instead of failing, switching away kills the ffmpeg process and deletes its temp files, and a healthy channel is completely unaffected. (Follow-up: confirmed the installer size impact directly — the Windows installer grew from ~82MB to ~103MB.)
- **0.5.0** worked through most of the outstanding list in one pass: recently-watched now has a real UI (a "Recently Watched" strip above Favorites); the EPG search box also matches already-loaded programme titles, not just channel names; short-EPG fetches are capped at 4 concurrent via a queue in the store; both the main EPG grid and the fullscreen channel bar now support arrow-key/Enter navigation (`EpgGrid.tsx`, shared by both); locked categories are namespaced by section (`"live:12"` vs `"movies:12"`) with a migration that drops legacy bare IDs rather than guessing which section they meant; Escape handling is fully centralized in App.tsx (Player.tsx now only owns M/arrow-key shortcuts, eliminating the class of bug where two uncoordinated listeners raced on the same key); the channel bar now falls back to a placeholder entry if the active channel isn't in the last-browsed category; and the audio-transcode fallback (0.4.8) now also covers the small preview panel, not just the fullscreen player, via a shared `useTranscodeFallback` hook. Also fixed a real Picture-in-Picture bug found while testing: PiP already opens a genuine floating OS window (confirmed with a real desktop screenshot — it renders on top of other apps, not just inside this one), but closing the player or switching channels while PiP was open left that window floating on the desktop indefinitely, frozen on the last decoded frame; it now exits automatically, but only on a genuine channel change, not an internal same-channel reload (network reconnect, the transcode fallback), which would otherwise have kicked users out of PiP unexpectedly. Also discovered and removed a dead code path: `ChannelList.tsx` still had a full "live channel list" branch (with its own row rendering, EPG lookups, etc.) left over from before 0.3.1 removed the separate live list — App.tsx never actually renders `ChannelList` on the Live TV tab anymore, so that branch could never run.

- **0.6.2** closed the parental PIN's threat-model gap: it's now encrypted at rest via Electron's `safeStorage` (OS keychain — macOS Keychain, Windows DPAPI, Linux Secret Service where a keyring daemon is running), with new main-process IPC handlers since `safeStorage` isn't reachable from the renderer directly. An existing plaintext PIN is detected and migrated to encrypted form the moment settings next load, not left to wait for some unrelated setting to change; falls back to plaintext if OS encryption genuinely isn't available (documented, not silent) rather than losing the feature, and treats an undecryptable value (e.g. a userData folder copied to a different machine) as unset rather than a permanent lock with no recovery path. Zero JS errors.

- **0.6.3** fixed the entire VOD/Series movie catalog playing with completely silent audio — confirmed via `ffprobe` sampling multiple titles that essentially every movie carries EC-3/E-AC-3 (Dolby Digital 5.1) audio, the same underlying codec 0.4.8 already handles for Live TV, but showing up completely differently here: VOD/series play through a native `<video src>` element (not hls.js), which gives no error event at all for this — the video decodes and plays perfectly, the audio track just never decodes, with nothing on `video.error` or in the console to say so. Detection is now a poll (`webkitVideoDecodedByteCount`/`webkitAudioDecodedByteCount`, requiring two consecutive silent ticks before concluding it's the codec failure rather than a startup race) since there's no error to hook into, reusing the same ffmpeg-remux-to-AAC fallback with VOD-appropriate HLS flags (`-hls_playlist_type vod`, a real end marker, instead of Live's rolling delete-and-continue window). Reaching a genuinely working fix took extensive live debugging against the real account and turned up three real bugs along the way. First: ffmpeg was auto-mapping the movie's embedded subtitle track, which made the HLS muxer defer writing the *main* playlist.m3u8 until the entire file had been processed rather than incrementally per segment — every earlier "timeout" in this investigation was actually this, not a network problem, only found by confirming live that ffmpeg fully transcoded a 76-minute movie at 19x realtime, writing hundreds of segments, while playlist.m3u8 itself never appeared until the process was killed; fixed by explicitly mapping only video+audio (`-map 0:v:0 -map 0:a:0`). Second: the proxy's `.pipe()` only ever propagates data forward, so an upstream connection was left running indefinitely once the client side abandoned it — invisible on an unlimited-connections account, but fatal on this one (confirmed via `get_server_info`: `max_connections: "1"`), since the still-open connection kept the account's single slot occupied; fixed by destroying the upstream request on any client-side close, not just success. Third: switching titles while a transcode was still spawning left the old ffmpeg process orphaned and running — the renderer only learned a session's ID once `transcode:start` resolved, which can take minutes, so `reset()` had nothing to cancel; the renderer now generates the session ID up front and registers it immediately, so a mid-flight switch actually cancels the abandoned attempt instead of leaving it to compete for the same connection slot. A fourth attempted fix — killing a transcode after a period with no ffmpeg stderr output, on the theory that silence meant it was stuck — was tried and reverted: ffmpeg's stderr is a pipe, not a tty, and its C stdio buffers a pipe's output fully rather than line-by-line, so a long silence doesn't reliably mean no progress (confirmed live, repeatedly: attempts with 60-120+ seconds of apparent silence had already opened the input and were moments from succeeding). Replaced with a single, generous flat deadline instead (240s for VOD, informed by real observed input-probe times of 25-90+ seconds on this account, against fast actual encode throughput of 19x realtime once running). Each fix was independently confirmed via live testing against the real account, but a single fully clean end-to-end pass could not be reproduced in the final verification round — the test account's connection reliability degraded visibly over the course of this debugging session (increasingly severe failure modes, ending in `net::ERR_HTTP2_PROTOCOL_ERROR` on the very first, non-transcode request), consistent with the provider throttling or rate-limiting an account reconnected dozens of times in under an hour by automated testing rather than a code issue. Worth a follow-up manual spot-check once the account has had time to rest.

- **0.6.4** found the actual root cause behind every VOD transcode timeout — 0.6.3's subtitle-mapping fix was real but wasn't it. Confirmed directly with an isolated, network-free ffmpeg test (a synthetic test pattern, no origin server involved): `-hls_playlist_type vod` is HLS-spec-correct behavior, not a bug — a VOD playlist must be published complete and unchanging per the spec, so ffmpeg withholds writing it to disk *at all* until the source hits EOF. For a two-hour movie, that's nowhere near any reasonable timeout regardless of network speed; a live test session wrote 200+ segments while `playlist.m3u8` never appeared once, then timed out right on schedule. `-hls_playlist_type event` is the type actually meant for "segments keep appending until the source ends," and writes the playlist incrementally after every segment (confirmed via ffmpeg's own log showing repeated `Opening playlist.m3u8.tmp for writing` during encode, not just at exit) — hls.js already knows to keep reloading an EVENT playlist until it sees the end marker, so this needed no player-side change at all, just the one ffmpeg flag. Also hardened the local proxy against a second, unrelated failure mode hit while chasing this down: Chromium's own network stack got stuck mid-session such that *every* request to the origin hung forever — reproduced with a plain renderer-side `fetch()` bypassing the proxy entirely hanging identically, while `curl` to the exact same URL from the same machine succeeded instantly and repeatedly, confirming the origin was healthy and something in that process's own DNS/connection state wasn't. The proxy previously had no timeout at all on the upstream request, so a hang like that was permanent, unrecoverable without restarting the app; it now gives up after 20s of no response headers, clears the session's host resolver cache, and retries once before failing. Verified end-to-end against the real account on the exact title that had been failing across every attempt: video and audio both confirmed decoding and growing in lockstep over a sustained 60+ second window, `currentTime` advancing at realtime pace, zero console errors. Worth noting for whoever picks up the next audio/transcode issue: when ffmpeg output looks stuck, check `-hls_playlist_type` (or more generally, whether the *player* mid-stream expects incremental writes) before assuming a network or connection problem — that assumption cost most of two release cycles here.

- **0.6.5** fixed a real crash a user hit directly: a "JavaScript error occurred in the main process" popup, with neither video nor audio playing. Root cause was in 0.6.4's own stuck-connection retry — `session.defaultSession.clearHostResolverCache()` returns a Promise (an IPC round-trip to the browser process), and it was being called fire-and-forget with no `.catch()`. A rejection there became an unhandled rejection in the main process, which is exactly what produces that dialog. Fixed with `.catch(() => {})`. While reproducing this, found a second, related correctness gap in the same code: the upstream timeout only called `.destroy()` on the stuck request and relied on that reliably emitting `'error'` to trigger the retry — but Electron's `net.ClientRequest`, built on Chromium's network stack rather than Node's `http` module, isn't guaranteed to fire one just because JS-side `.destroy()` was called. If it doesn't, the request stays permanently unsettled — no response, no error, and whatever's waiting on it (ffmpeg, the renderer) hangs forever, indistinguishable from the original bug the timeout exists to fix. The retry/failure logic is now a single function the timeout calls directly, guaranteeing it actually runs rather than depending on an event that might not fire. Also added global `uncaughtException`/`unhandledRejection` handlers in the main process as a safety net (previously there were none at all) — confirmed directly useful in the same test session: a genuine `net::ERR_HTTP2_PROTOCOL_ERROR` surfaced as an uncaught exception from a lower level than any per-request handler reaches, and would have crashed the app before this; instead it was logged and the retry path recovered on its own. Verified end-to-end against the real account on the exact title that had been failing and crashing: video and audio both confirmed decoding and growing over a sustained 48+ second window immediately after the retry path recovered from a live protocol error, with no crash. Lesson for next time a fire-and-forget Electron API call gets added anywhere in the main process: check whether it returns a Promise before assuming it's synchronous — `clearHostResolverCache()` looks like a simple cache-clear call and isn't one.

- **0.6.6** turned out to be a UX gap, not a functional bug, behind what looked like a fourth consecutive failure on the same title: a user report of "plays for a second then goes black, still not working" was reproduced exactly, live, repeatedly — but in every reproduction the fix actually succeeded, just not within the ~30 seconds a reasonable person would wait while staring at a small spinner. The black screen itself is intentional (the video is deliberately detached before the transcode starts, to avoid a connection conflict — see 0.6.3), but for this specific title, the audio-fix step can take anywhere from ~10 seconds to a couple of minutes depending on how the connection to the provider is behaving that moment, and the generic "Fixing audio for this channel…" wording (written with Live TV's normally-fast fallback in mind) gave no reason to expect a wait that long. Movies/series now get their own wording — "this can take a minute or two on a slow connection" — so the wait reads as expected behavior instead of a hang. Worth remembering for the next report that looks like a regression: confirm whether the underlying operation actually failed before assuming the fix regressed, especially for anything with a wait state and no progress indicator.

- **0.6.7** followed up on a report that looked like a regression but wasn't. A user hit "still not working, no video or audio" on the same title as 0.6.6, alongside two console errors: `net::ERR_NETWORK_CHANGED` (Chromium detecting a real network interface change on their machine — Wi-Fi reconnect, sleep/wake, VPN toggle; genuinely external) and `Transcode cancelled` (the fallback's own abandon-on-switch logic from 0.6.3, working as designed if the player was closed or switched mid-wait). Reproduced the exact title three times, hands-off, no interference — it succeeded every time, between ~10s and ~70s. The actual gap: 0.6.6's improved wording set the right time expectation in words, but the spinner itself still looked identical whether it was 5 seconds in or genuinely stuck, with zero real progress to report (ffmpeg is either still opening the source or still probing it during this whole window). Added a live elapsed-time counter to the message instead — the only honest signal available for a wait like this — so a user can see it's still counting rather than guessing whether it's frozen. Lesson: for a wait state with no real progress metric, don't stop at wording the uncertainty away — show the one signal that actually exists (time), or a "not stuck" report will keep looking identical to a "stuck" one.

- **0.6.8** found and fixed the real, final piece behind this whole run of VOD-transcode issues — and it took a user directly pushing back with "this title plays fine in another IPTV app" to get there, which turned out to be the key piece of evidence: another client using the same account handles this title with no issues, so the file and provider aren't the problem, meaning something in this app's own connection handling had to be. Captured a live reproduction's full console output at the user's request and found two things in the same code path. First, a real crash: the 20s upstream timeout (0.6.4) would give up on a byte-range request and answer the client, but Electron's networking sometimes *still delivered the real response* afterward — proof the connection wasn't actually dead, just slower than 20s — and that late arrival tried to write response headers a second time on an already-finished response, crashing the whole main process with `ERR_HTTP_HEADERS_SENT`. Fixed by ignoring any response that arrives after an attempt is already settled, regardless of timing. Second, given that same evidence, raised the timeout itself from 20s to 45s — 20s wasn't just occasionally too tight, it was cutting off requests that would have gone on to succeed. Notably, the reproduction that surfaced this bug *still worked* — 900+ segments over nearly 8 minutes of healthy, sustained transcoding — because ffmpeg's own internal retry happened to route around the exact race condition being fixed here. That was luck masking a real bug, not evidence of a working system; worth remembering next time something "works but with a scary error in the log" — the error is real even when the outcome looks fine. Also worth remembering for future reports: "another app handles this fine" is a specific, checkable claim (same account, same file, different client) — it rules out root causes that comparing this app against its own history alone can't.

- **0.6.9** fixed the VOD/series audio-fix transcode's video visibly skipping ahead with no user input, reported live by a user actively watching. Root cause: hls.js only knows a playlist is genuinely finished once it sees `#EXT-X-ENDLIST` — until then it's "live" regardless of *why* the tag is absent, and the transcode fallback's own growing output (0.6.4's `-hls_playlist_type event`) has no ENDLIST for as long as ffmpeg is still working through the source. The same hls.js instance also plays real Live TV, configured (correctly, for that case) to force a seek forward whenever playback falls too far behind the live edge — but for the fallback's own movie/series output there is no live edge, only wherever ffmpeg currently is, and since `-c:v copy` lets ffmpeg encode at 19-50x realtime, a normal 1x viewer falls behind that "edge" by more than the threshold within under a minute, triggering repeated forced seeks with zero input. Fixed by only applying the live-edge config when the content is actually Live TV; the fallback's own instance gets those settings inflated far enough to never trigger. Verified this correctly *without* depending on another live reproduction against this account's currently flaky connection — traced hls.js's own `liveSyncPosition` source directly and confirmed the formula's min-clamp mathematically guarantees the computed position can never land ahead of the start of available content once `targetLatency` is inflated this far. Worth remembering: when a live account test is unreliable, checking a library's own source for what a config value actually does can be more conclusive than another reproduction attempt — and faster.

- **0.7.0** added an optional VPN feature, off by default, for routing this app's own connection to the Xtream server through OpenVPN — split-tunnel, not a full system VPN. Settings now holds a list of named profiles (each an `.ovpn` file plus optional username/password, encrypted at rest the same way as the parental PIN), with one active at a time; activating a different profile tears down the current tunnel first. The design deliberately avoids a persistent privileged daemon: connecting spawns `openvpn` via `sudo-prompt` (a one-shot elevated command, no live process handle), so control after that point goes through OpenVPN's own local management-interface socket (`--management` + `state on`) instead — auth prompts, connection-state transitions, and a clean `signal SIGTERM` shutdown all flow over that same unprivileged socket. Split-tunneling itself needed more than `--route-nopull`: a real test config (a genuine commercial VPN's `.ovpn` file) had `redirect-gateway def1` written directly in the client file, which `--route-nopull` doesn't touch since that flag only suppresses server-*pushed* routes, not the client's own. OpenVPN's `redirect-gateway` installs two `/1` routes (`0.0.0.0/1`, `128.0.0.0/1`) rather than replacing the literal default — so the fix captures the machine's real default gateway before connecting (`route -n get default` / `ip route show default` / `route print -4 0.0.0.0`, by platform) and has a `--route-up` script explicitly delete those two routes and restore the original default before adding one narrow host route to the Xtream server through the tunnel. Also fixed two real robustness gaps found via live testing against that config: an elevated shell's `PATH` can be far more minimal than the user's own (a real "openvpn: command not found" even though the same user's normal terminal found it fine after installing) — `findOpenvpnBinary()` now checks known install locations directly, including scanning Tunnelblick's bundled binary path for users without Homebrew, before falling back to `which`/`where`; and `vpn:connect`'s IPC handler previously always resolved even when the connection genuinely failed internally (the status-changed push event disagreed with the promise), now checked and rethrown explicitly. Bundling the `openvpn` binary itself (raised and explicitly declined for this release) was researched: macOS/Linux need no separate driver anymore and Windows could avoid the old TAP installer via Wintun, but there's no ffmpeg-static-equivalent source of prebuilt cross-platform OpenVPN binaries — this release continues to require it already installed. Verified the new multi-profile Settings UI end-to-end via a live CDP-driven test (add/edit/save/remove all round-tripping correctly through disk, including the encryption boundary) — one CDP-only false alarm along the way: a background-launched, OS-unfocused window doesn't reliably fire native blur/focusout events, which briefly looked like the profile-rename autosave was broken until the identical code path was confirmed working via a button click instead. The actual elevated connect flow itself couldn't be exercised by automation (a real Touch ID/admin dialog needs a human), so the split-tunnel routing behavior should get one real hands-on check against an actual profile before being considered fully proven in this exact UI.

- **0.7.1** fixed a real connect failure found the moment 0.7.0 got its first genuine live test against an actual commercial VPN account: `sudo-prompt`'s elevated command failed with a content-free "Command failed" error. Reproducing the exact invocation directly (outside the app, via a standalone script run under Electron's own Node runtime) isolated two real bugs. First: OpenVPN has no `--route-down` option — the flag that runs a script before routes are torn down is `--route-pre-down`; the made-up flag made OpenVPN reject the whole command line at option-parsing time and exit immediately, which is exactly what surfaced as the useless generic error. Second: nothing told OpenVPN where to resolve the config's relative `ca`/`cert`/`key` paths from — this exact test config (and many real providers') reference them as bare filenames, resolved against OpenVPN's own working directory, not necessarily where the `.ovpn` file lives; added `--cd <config's directory>` so they resolve regardless of the elevated shell's actual cwd. Also stopped discarding real diagnostics on failure: `sudo-prompt`'s callback carries stdout/stderr, previously ignored in favor of its own content-free message, and the `--log` file was being deleted by cleanup before anything ever read it — both are now captured and surfaced.
- **0.7.2** found the actual remaining cause after 0.7.1's fixes still failed live, with `sudo-prompt` again returning completely empty stdout/stderr/log despite the identical command succeeding perfectly under plain interactive `sudo` in Terminal. Isolated methodically: `sudo-prompt` itself works (a standalone trivial-command test, run outside the app), a long/complex command shaped just like the real one works, `openvpn --version` runs fine elevated — so the library, command length/quoting, and basic binary execution were all ruled out. Dropping `--daemon` briefly (to see OpenVPN's own stdout directly instead of only its `--log` file) surfaced the real message: `"Error opening configuration file"` for a file `sudo` had just opened seconds earlier from the identical path. The one relevant fact: that config lived under `~/Desktop`. macOS's TCC privacy protection blocks *even root* from reading files under Desktop/Documents/Downloads when elevated via this app's AppleScript-based "administrator privileges" mechanism specifically so `sudo`/root can't be used to route around user consent for those folders — confirmed live by copying the identical config outside those folders and watching the identical command succeed immediately. Fixed by having `startVpn()` copy the config (and whatever files it references by relative path) into the per-connection temp directory it already creates — already proven reachable under this same elevation — before ever invoking OpenVPN, regardless of where the user's original file lives. Also found and worked around a real bug in `sudo-prompt` 9.2.1 itself along the way: its macOS result handler drops stdout/stderr entirely on any non-zero exit before they reach the caller's callback, regardless of what the failed command actually wrote — a trap for anyone debugging a future elevated-command failure on macOS via this library.
- **0.7.3** added `.zip` support to "+ Add VPN configuration" — most real-world providers (this app's own test config included) distribute a `.ovpn` alongside separate `ca`/`cert`/`key` files bundled in a zip, not as one self-contained file. Importing (whether from a zip or a direct `.ovpn` pick) now always copies into a directory this app owns under `userData`, instead of referencing the original location in place — this also protects against the original file later moving or being deleted, on top of sidestepping 0.7.2's TCC restriction regardless of where the picked file started; removing a profile now cleans up its imported directory (scoped defensively to only ever delete inside `userData/vpn-profiles`, since a profile added before this change can still point at the user's own original file location). Building this surfaced a real path-traversal gap in the already-shipped `importVpnConfigInto`: a `.ovpn` file's own `ca`/`cert`/`key` directives were joined onto directories with no containment check, so a crafted `ca ../../../../etc/passwd`-style directive could read arbitrary files into the connect-time temp dir or escape it on the write side — worth closing regardless of the zip feature, since a `.ovpn` is exactly the kind of file people import from community sources; added a `safeJoin()` that refuses anything resolving outside the intended base directory, verified against a real traversal attempt. Also mitigated `extract-zip`'s own known, currently-unfixed vulnerability (GHSA-jmr9-qjv8-65gv, symlink-based path traversal — no patched version exists upstream): the extracted tree is walked afterward and the whole import is refused if any entry is a symlink, verified against a crafted symlinked zip entry. Separately, fixed a real elevation-prompt regression reported live: the app was asking for OS admin approval on ordinary launch, not just when the VPN was explicitly activated. Root cause: `connect()` (which runs automatically on every launch to restore the last Xtream profile) unconditionally re-fired `activateVpnProfile()` in the background whenever a profile had been left active from a previous session. Removed entirely — activation now only ever happens from an explicit Activate click, matching this feature's original least-privilege intent; a profile marked active in settings is a saved choice for next time, not a standing instruction to auto-elevate on launch. With this release, the VPN feature has been live-verified end-to-end against a real commercial account: elevation, config/cert import, credential auth, and OpenVPN's own TLS handshake all confirmed working — the only remaining failure seen in testing (a TLS handshake timeout) traced to the test machine's corporate network DNS-sinkholing the VPN provider's hostname, an intentional employer security policy outside the app's control, not a bug.

- **0.7.4** fixed a real Windows-only failure found on 0.7.3's first live Windows test: OpenVPN reported it couldn't find `ca.crt`/`client.crt`/`client.key` even though `--cd` correctly pointed at the directory they should have been copied into. Root cause: `safeJoin()` (0.7.3's path-traversal containment check) hardcoded a forward slash to verify a copied file's resolved path stayed inside its destination directory — `path.join()` uses backslashes on Windows, so the check silently rejected every legitimate relative reference there, and the copy step skipped all three files with no error at all. Fixed by comparing against `path.sep` instead; verified against simulated Windows paths (via Node's `path.win32`, without needing an actual Windows machine) that legitimate references now resolve correctly while traversal attempts, in both slash styles, are still rejected exactly as before — a reminder that a security fix itself needs cross-platform verification, not just the vulnerability it closes. Also added a "Retry" button to the app's error banner, prompted by a live report that a broken proxy connection required quitting and relaunching the whole app to recover from — `retryConnection()` re-runs the exact same connect flow (re-target the proxy, re-authenticate, reload Live TV) against whichever profile was last active, without needing a restart.

- **0.7.5** fixed the next real Windows-only failure, found immediately after 0.7.4's cert-copy fix cleared the way: OpenVPN exited instantly with `daemon() failed or unsupported: Bad address (errno=14)`. OpenVPN's Windows build simply has no `--daemon` support at all — there's no `fork()`/daemonize model on Windows to begin with, unlike macOS/Linux where `--daemon` had worked in every prior test. `--daemon` exists specifically so the one-shot elevated command (`sudo-prompt` gives no live process handle back) returns quickly while OpenVPN keeps running in the background; reading `sudo-prompt`'s own Windows implementation showed its elevation path runs the command inside a `.bat` file and explicitly waits for it to exit before reporting anything back, so without a working `--daemon`, that wait would simply never end. Fixed by dropping `--daemon` on Windows and instead wrapping the whole invocation in `start "" /B`, which launches `openvpn.exe` as a genuinely separate process the `.bat` doesn't block on — the empty `""` is required, since `start`'s first quoted argument is always taken as a window title if omitted, which would have silently swallowed the real command. Not yet live-verified on Windows (this fix landed between live test rounds) — worth confirming it actually reaches a connected tunnel there, not just past the immediate crash.

## Player controls

- **Audio track selection, subtitle support, and manual quality-level selection** are all still worth building eventually — the code shape is straightforward (hls.js exposes `audioTracks`/`subtitleTracks`/`levels` directly, and the Stats overlay already reads the last of those three for display) — but 0.6.1 confirmed the real test account's provider serves a single flat rendition per channel with no alternate tracks, so there's currently nothing for any of these to let a user pick between. Revisit if testing against a different provider (or this account's catalog turns out to be more heterogeneous than the 4-channel sample checked), not before.

## VPN

- **Player/stream traffic isn't confirmed to route through the tunnel — only the API calls the connect flow itself makes.** Raised directly in 0.7.7: the local proxy's upstream request used `redirect: 'follow'`, and the split-tunnel route (0.7.0) only covers the single IP resolved for the Xtream hostname once, at connect time. If a provider's panel ever redirects actual stream delivery (not just API responses) to a different host — common with CDN-backed IPTV panels — that traffic would silently bypass the tunnel while looking, from the UI, exactly like everything else did go through it. Still not fixed, but 0.7.8 makes it instrumented rather than invisible: the proxy switched to `redirect: 'manual'` and now inspects every redirect's target host itself before following it, warning (once per off-tunnel host per connection, both to the console and as a dismissible in-app banner — `vpn:stream-route-warning`, alongside the existing disconnect warning in what's now `VpnWarnings.tsx`) whenever a hop lands somewhere other than `vpnRuntime.tunneledHost`. This still doesn't close the gap — a warned-about redirect is still followed and still bypasses the tunnel either way — it only answers the open question of whether this happens at all for a given provider. Next real step is watching for that banner during an actual VPN-connected viewing session; if it never fires for the providers in use, this item can likely be closed as a non-issue. If it does fire, closing it for real would still mean either resolving and routing every host the proxy ever actually talks to (not just the original one), or having the proxy refuse a response from an unexpected host while the VPN is meant to be active.
- **Confirm split-tunnel routing specifically holds on Windows, not just that the tunnel connects.** 0.7.6 confirmed OpenVPN reaches a genuine CONNECTED state on Windows (green, no error) — the first real end-to-end success there — but that only proves the tunnel itself works, not that the route-up/route-pre-down `.bat` scripts (0.7.0's gateway-capture-and-restore logic, Windows-batch-syntax and never live-tested until now) actually keep ordinary browsing on the normal gateway while only the Xtream server's traffic goes through the tunnel. Worth one explicit check next time: compare `route print` before/during/after a connected session.
- **Investigate whether a failed/reconnecting VPN attempt can leave the Xtream server unreachable even after the tunnel gives up.** Reported live on Windows: after a VPN activation failed, the app's connection to the Xtream server was also lost (a 502), previously requiring a full app restart to recover — 0.7.4's Retry button fixes the *symptom* (no more restart needed), but the actual mechanism was never confirmed. One real candidate: if OpenVPN ever reaches far enough to run `--route-up` (adding a narrow host route to the Xtream server through the tunnel gateway) and then drops into `RECONNECTING` rather than exiting outright, `--persist-tun`/`--persist-key` keep that route in place while the gateway behind it is down — silently black-holing the proxy's own attempts to reach the same IP by any other path, independent of the tunnel. Worth confirming directly next time it happens: check the OS routing table for a stale host route to the Xtream server's IP while the app is in this broken state.
- **Bundling OpenVPN itself, revisited.** Explicitly declined for 0.7.0 in favor of shipping now — this release still requires OpenVPN already installed (Homebrew or Tunnelblick on macOS, the official installer on Windows/Linux). If this becomes a real onboarding friction point, the earlier research holds: macOS/Linux need no separate driver install anymore, and Windows could self-install a driver silently via Wintun instead of the old TAP installer — the actual blocker is that there's no ffmpeg-static-equivalent source of prebuilt cross-platform OpenVPN binaries, so bundling would mean standing up a real CI cross-compilation pipeline, not a quick dependency add. Also carries a GPLv2 "mere aggregation" obligation (license text + source offer for the exact binary shipped) if ever pursued — worth noting this project may already have the same unaddressed obligation from `ffmpeg-static`'s own binaries, independent of OpenVPN.

## Playback quality

- **A "channel is currently broken" surface.** Still relevant for whatever *doesn't* get fixed by the transcode fallback (a genuinely dead stream, an unsupported video codec, etc.) — there's still no way to know a channel is bad without trying it. Nothing to build proactively here yet (no data on how common this is across a real catalog), but worth watching if it turns out to affect more than a handful of channels.
- **The proxy's stuck-connection retry (0.6.4) is still a mitigation, not a confirmed single root cause — because there turned out to be more than one.** 0.6.8 directly proved at least one contributing case: a request some code path was treating as "hung" was actually just slower than the timeout allowed, with a real response arriving late. That doesn't rule out the *other* mechanism 0.6.4 was chasing (every request to a host hanging forever with zero response at all, reproduced independently of this proxy) — the two may well be separate failure modes that happen to look similar from a fixed timeout's perspective. If a hang recurs in a way 45s + one retry doesn't catch, the next step is still capturing a `chrome://net-export` log from a live reproduction rather than tuning the timeout again — that's the only way to tell which mechanism (or a third one) is actually in play this time.
- **Lighter-weight ffmpeg bundling.** Confirmed in 0.4.8: bundling `ffmpeg-static` grew the Windows installer from ~82MB to ~103MB (other platforms similarly). Worth considering a system-ffmpeg-if-present check that falls back to the bundled binary only when needed, if installer size turns out to matter to users on slower connections — not urgent, just now has a real number attached to it.
- **Subtitles are dropped entirely once the VOD/series audio-fix transcode kicks in (0.6.3).** The fallback explicitly maps only video+audio (`-map 0:v:0 -map 0:a:0`). Investigated properly in 0.7.10 with isolated, network-free ffmpeg tests (synthetic video+AC-3 audio+SRT subtitle input, run directly against the exact bundled `ffmpeg-static` 6.0 binary this app ships) rather than attempted blind — found real progress, but also a real blocker that's still unresolved:
  - Mapping the subtitle track (`-map 0:s:0 -c:s webvtt`) alongside video+audio in a flat `-f hls` output (no `-var_stream_map`) does *not* reproduce 0.6.3's deferred-playlist bug on this ffmpeg version — `playlist.m3u8` still writes incrementally, confirmed the same way 0.6.4 confirmed the original bug (watching segments accumulate in real time via a `-re`-throttled synthetic input). Whatever caused the original bug, it either doesn't reproduce with an explicit `-c:s webvtt` codec, or was specific to a subtitle format/ffmpeg version this test didn't reproduce.
  - That flat layout is a dead end anyway: its WebVTT rendition (`playlist_vtt.m3u8`) is never referenced anywhere inside the flat `playlist.m3u8` a player is actually given, so it's structurally undiscoverable — a real HLS master playlist (`-var_stream_map "v:0,a:0,s:0,sgroup:subs"` + `-master_pl_name`) is genuinely required for a player to ever find the subtitle track at all. Confirmed that layout *also* writes everything incrementally when a subtitle stream exists.
  - The actual blocker: `-var_stream_map` referencing `s:0` hard-fails the whole ffmpeg process ("Unable to map stream at s:0") the instant the source has no subtitle track — even with ffmpeg's own optional-map syntax (`-map 0:s:0?`) correctly producing zero subtitle output streams first. Confirmed with matched pairs of tests (same command, one input with a real subtitle track, one without). A from-one-input two-separate-outputs workaround (video+audio always, an independent optional subtitle-only `-f hls` output) was also tried and found *unreliable in the opposite direction* — it failed ("No streams to mux were specified") specifically when a subtitle track *was* present and mapped, the reverse of what's needed, and not chased further without understanding why.
  - So safely choosing the right ffmpeg command shape requires knowing up front whether the source has a mappable subtitle track — and there's no cheap way to know that. This app's own Xtream API calls carry no subtitle metadata (there's no `get_vod_info` call today, and Xtream panels don't expose per-stream subtitle presence at the catalog level regardless), so the only way to find out is to actually open the file — the same expensive step (25-90s observed on this account, per 0.6.3) `startTranscode` already treats as its dominant cost. A "try with subtitles, retry without on the specific failure" approach would be *correct* (the failure happens fast, right after the initial probe, before any output exists) but would double that wait for every title that doesn't have embedded subtitles — likely the common case — which is a real regression traded for a minority-case feature, not a free win.
  - Not attempted further this round. Next step would be either finding a genuinely cheap way to know subtitle presence before committing to a muxer layout, or live-testing the double-open-cost trade-off against a real account to see whether it's actually acceptable in practice rather than assuming it isn't.
- **A single-connection account puts Live TV's and VOD's audio-fix fallbacks in the same failure class.** 0.6.3 traced VOD's transcode timeouts back partly to a real account cap (`get_server_info`: `max_connections: "1"`) combined with a proxy bug that left an abandoned connection open indefinitely — now fixed, but the underlying constraint (one slot, shared by whatever's currently playing and whatever ffmpeg needs to open) isn't going away for accounts like this one. Live TV's fallback has less exposure here since the source it replaces is already broken and mostly idle by the time it fires, but it's the same class of risk. 0.7.9 surfaces this rather than leaving it silent: `connect()` now records `singleConnectionAccount` from `authenticate()`'s own `user_info.max_connections` (already fetched at login, no extra request), and Player.tsx uses it two ways — the VOD "Fixing audio…" wait grows a secondary line once it's run past 60s explaining the account-cap risk, and a failed VOD audio-fix's error message gets the same explanation appended. Not live-verified against a real single-connection account (this repo's own test account already has this cap, per the 0.6.3 note above, but wasn't re-tested live for this specific change) — worth a real check that both messages actually appear as expected next time a VOD transcode is exercised against it.

## Compatibility

- **Raw M3U + separate EPG XML URL support.** Some providers hand out an M3U playlist URL and an EPG XML URL instead of full Xtream Codes API credentials. Supporting that as an alternate connection type (a second tab on `LoginScreen`, a simple M3U parser alongside `lib/xtream.ts`) would widen compatibility beyond Xtream-specific panels. Not attempted yet — no M3U source was available to test against, and it's a meaningfully different data model that deserves its own real-provider validation rather than a guess.

## Packaging & distribution

- **Code signing & notarization.** Unsigned installers trigger Gatekeeper warnings on macOS and SmartScreen warnings on Windows — and macOS's Squirrel-based auto-updater specifically **won't apply updates at all** to an unsigned/unnotarized app, so this is a hard blocker for auto-update actually working on Mac, not just a polish item. Needs a paid Apple Developer certificate and (for Windows) a code-signing certificate; plug into `.github/workflows/release.yml` once available.
- **Windows on ARM installer — blocked, not just niche.** `ffmpeg-static`'s platform table (`node_modules/ffmpeg-static/index.js`) only lists `x64`/`ia32` for `win32`; there's no `arm64` Windows binary to bundle at all. Building one anyway would either fail the install step outright or silently package the x64 binary into an arm64 installer, which would only work via Windows' x64-emulation layer — not a real native build. Revisit only if `ffmpeg-static` adds arm64 Windows support upstream, or if the lighter-weight-ffmpeg-bundling item above ships first and changes what's actually being packaged.

## Quality

- **Expand test coverage.** vitest unit tests exist for `lib/xtream.ts`, `lib/epg.ts`, `lib/epgTime.ts` (the EPG grid's `pct()` math), `lib/storage.ts` (settings load/merge, locked-category migration, PIN encryption fallback), `lib/useTranscodeFallback.ts` (`isUnsupportedAudioCodecError`), and `useAppStore.ts` (locked-category namespacing, `submitPinAttempt`'s PIN comparison, the short-EPG concurrency queue's actual cap, `tvArchive` threading through `play()`), plus a CI job that runs typecheck/lint/test/build on every push. 0.7.11 closed the proxy gap named here previously: `startLocalProxy()`'s request-handling logic (retry/timeout, CORS/header rewriting, off-tunnel-redirect detection) moved out of index.ts's `handleProxyRequest` closure into a new `src/main/proxyServer.ts` — an extract-and-parameterize refactor, not a rewrite (every comment and the exact retry/timeout/redirect behavior moved verbatim), with all of its Electron dependencies (`net.request`, `session.defaultSession.clearHostResolverCache`, VPN state, transcode-file serving) injected via a `ProxyServerDeps` object instead of referenced directly. That makes the module fully Electron-free and testable against a real local HTTP server — `proxyServer.test.ts` spins one up per test plus a genuine Node `http.request`-backed stand-in for Electron's `net.request` (a real `EventEmitter`, since `req.pipe(upstreamReq)` needs generic stream-event support, not just the three custom events this code actually listens for), and covers CORS/OPTIONS handling, malformed-target-URL handling, Range forwarding, content-encoding/length/CSP stripping, the off-tunnel-redirect callback (fires only when genuinely cross-host *and* the VPN is connected, confirmed both negative cases), and the timeout+retry path actually recovering on the second attempt (with `upstreamTimeoutMs` made injectable so the test doesn't wait out a real 45s timeout) — 64 tests total as of 0.7.11. One real Electron-`.d.ts` gap surfaced along the way and got documented rather than worked around silently: `net.request()`'s bundled type declares only the older `.abort()`, omitting `.destroy()`/`.destroyed` even though both have genuinely existed and worked at runtime across many prior releases of this exact proxy — bridged with one explicit, commented cast at the single call site that constructs a real one, rather than loosening the new module's own interface to paper over it. Still untested: most of the rest of the store's actions (`connect`/`init`'s own control flow, VPN profile CRUD) and the transcode-spawning code in index.ts itself (`startTranscode`/`stopTranscode`), which still isn't decoupled from Electron the way the proxy now is.
- **A floating-promise lint rule would have caught 0.6.5's crash before it shipped — added in 0.7.9.** `eslint.config.mjs` now runs `@typescript-eslint/no-floating-promises` (and `no-misused-promises`, scoped off for JSX attributes/props specifically to avoid flagging this codebase's own idiomatic `onClick={async () => ...}` pattern) across both the main/preload and renderer source trees, wired into CI as a new `npm run lint` step right after `typecheck`. Turning it on surfaced 17 genuine pre-existing floating promises — mostly fire-and-forget calls to this store's own `save*`/`load*` helpers and to Electron APIs (`shell.openExternal`, `BrowserWindow.loadURL`/`loadFile`, `app.whenReady().then(...)`) — each fixed on a case-by-case basis: an explicit `void` for calls into something that already self-catches (e.g. `selectCategory`, `loadShortEpg`), a `.catch()` with a specific log message everywhere else, and one real gap closed along the way — `init()` itself had no top-level try/catch, so a storage-read failure during startup would have silently stuck the app on its initial screen with nothing but a console error; it now falls back to the same `status: 'error'` banner `connect()` already uses.
- **React's `autoFocus` doesn't work for dynamically-mounted elements.** A real gotcha hit while building 0.5.0's channel-bar keyboard nav: the JSX `autoFocus` prop relies on the browser's native autofocus-on-parse behavior, which only fires for elements present in the *initial* HTML parse — not for ones a React component inserts later via the DOM API, which describes almost every conditionally-mounted overlay in this app. `EpgGrid.tsx` now calls `.focus()` explicitly in a mount effect instead, and that's now the established pattern for anything else in this codebase that wants to autofocus on mount.
